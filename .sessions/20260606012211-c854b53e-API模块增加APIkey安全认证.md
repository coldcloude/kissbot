```markdown
## 方案设计

### 需求回顾

在 API 模块中添加安全认证能力，通过 HTTP header 传递统一 API key。内部通信（HTTPS/WSS），单用户，不需要用户系统。

### 方案 A（推荐）：API 层定义认证 trait + 校验结果类型

**思路**：在 `kissbot-api` 库中定义认证相关的数据类型和 trait，不对具体的校验逻辑做假设。各独立进程（memory-store、memory-ego、agent station 等）在启动 HTTPS 服务器时，通过 axum middleware 读取配置中的 API key，调用这个 trait 进行校验。

**组件设计**：
1. `kissbot-api/src/auth.rs` — 新增模块
   - `AuthError` 错误类型（枚举：MissingKey / InvalidKey）
   - `ApiKeyValidator` trait（`fn validate_api_key(&self, header: &str) -> bool`）
   - HTTP header 名称常量 `X-Api-Key`
   - `require_auth` 辅助函数（解析 header → 调用 validator → 返回 Result）
2. 各进程的 HTTPS 服务器侧：
   - 读取配置 → 实例化 `ApiKeyValidator`（简单比较：配置 key == 请求 header）
   - 注入到 axum middleware 中

**优点**：
- 不引入额外依赖
- `kissbot-api` 只定义契约，不绑定具体校验实现
- 各进程可在未来升级校验方式（如 key 轮换、多 key）而不改合约层

**Trade-off**：每个进程需自己实现 middleware 接入——但这就是一个 router layer 的事。

在 `kissbot-api` 中直接提供 axum middleware 函数，各进程直接引用。更省代码但引入对 axum 的依赖。
```

```markdown
好，现在我来分析两种方案：

**方案1：kai-ws 增加自定义 filter 接口**

在 `ws_handle_connection` 函数中，在 `accept_async(stream)` 之前增加一个 filter 回调。但是——`accept_async` 已经消费了 TcpStream 做了 HTTP Upgrade。想检查请求头，需要用 `accept_hdr_async` 替代 `accept_async`，它在握手完成后回调中暴露请求头供检查。

具体来说：
- `accept_hdr_async(stream, callback)` 中的 `callback: impl FnOnce(&Request, Response) -> Result` 可以检查头信息
- 如果在 callback 中拒绝，返回错误，握手失败

但这里有个问题：`kai-ws` 的 `ws_handle_connection` 当前直接调用 `accept_async(stream)`，不接触请求头。要支持 filter，需要：
1. 增加一个可选的 `WssRequestFilter` trait 参数
2. 改用 `accept_hdr_async`，在 callback 中调用 filter

**方案2：由使用 kai-ws 的程序在调用前自行验证**

也就是在 `listener.accept().await` 获得 `TcpStream` 后，在传入 `ws_handle_connection` **之前**，先手动读取 HTTP Upgrade 请求，检查 header，然后再把 stream 传给 `ws_handle_connection`。

- `kai-ws` 只定义一个 trait，不包含认证逻辑
- `kissbot-security` 实现 filter 做实际校验
- `kissbot-channel` 等使用者只需传入 filter 实例
```

## 对话 30 (2026-06-07 16:47:59)

### 用户输入

```markdown
tower库的作用是什么？axum必须用tower库吗？
```

### Claude 响应

````markdown
`tower` 是一个**通用的中间件抽象层**。它定义了 `Service` trait 和 `Layer` trait，让不同框架的中间件可以互相组合。

**`tower` 的作用：**
- `Service` trait：描述一个异步函数 `Request -> Response`，是中间件的基本单元
- `Layer` trait：一种"中间件工厂"——把一个 `Service` 包一层，变成新的 `Service`

**axum 和 tower 的关系：**
- axum 的 `Router` 本身实现了 `tower::Service`，axum 的中间件体系完全基于 `tower::Layer`
- 所以严格来说不是"必须用"，但**官方推荐的方式就是通过 tower 的 Layer 机制**——这也是 axum 社区的标准做法

**当前 `kissbot-security` 的做法分析：**

我现在是手动实现 `tower::Layer` 和 `tower::Service` 来做中间件，确实用了 tower。但 axum 还有一种更简洁的方式——直接用 **axum middleware**，通过 `axum::middleware::from_fn` 传一个函数就行了，不需要手动实现 Layer/Service。

比如：

```rust
use axum::{
    middleware,
    routing::post,
    Router,
};

async fn auth_middleware<B>(
    mut request: axum::extract::Request,
    next: middleware::Next<B>,
) -> axum::response::Response {
    // 检查 header...
    let auth = extract_api_key(request.headers());
    if auth.is_err() {
        return (StatusCode::UNAUTHORIZED, Json(...)).into_response();
    }
    next.run(request).await
}

// 使用时：
Router::new()
    .route("/api", post(handler))
    .route_layer(middleware::from_fn(auth_middleware))
```

这样不需要 tower 依赖，更简洁。你觉得改不改？
````
