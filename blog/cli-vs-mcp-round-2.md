# CLI 和 MCP 之争

2026年年初，我做过一次简单的对比，CLI和MCP和SKILL。当时CLI势头正盛，主打理念就是人和Agent使用相同的方式操作，可以复用前人在CLI上多年的积累。但半年过去，现在看来，这点优势并不是决定性的。

并且当时有一个重要的理解错误——Tool和CLI的关系。实际上，CLI无法取代tool，也不可能取代tool，因为CLI根本就是依赖tool执行的，是通过各Agent的命令执行tool，如Bash工具，来执行的。

一个正常的tool，是自带描述的，LLM可以根据描述判断是否调用这个工具、传什么参数。但CLI本身没有任何说明，经常被当作CLI优势的，可以在调用时打印用法，现在看来更加没有效率——为了使用一个CLI竟然要调两次LLM！第一次，需要先执行一个--help的tool call查看用法，再执行第二个tool call完成实际需求。

因此在这种场景下，SKILL从可选变成了必需。只有在SKILL.md中写明了CLI如何使用，才可以使LLM不生成查询用法的tool call。而反观MCP，他是自描述的。只访问MCP服务本身，就可得到调用所需的各tool的描述——而这发生在agentic loop之外。

此外，MCP还有个巨大的优势，那就是它持久化运行。CLI的调用是一次性、单线程的。想要保存调用过程中的状态，只能依赖外部存储系统。比如agent-browser的CLI，想要保存网站的登录信息，只能复用浏览器的LocalStorage，否则这些信息将随着CLI进程的终止而消失。而MCP是服务器，天然就是独立的进程，任何状态都可以保存在服务器进程里。

最后，对比上次的核心结论——CLI可以保证用户和agent使用的一致性，而人无法直接使用MCP。但这实际MCP不过就是HTTP+JSON，人本实际也可用curl命令就可以调用。更不用说，当前的AI能力分分钟就可以基于MCP的HTTP接口，直接生成对应的REST请求的管理页面。
