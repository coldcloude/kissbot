# kissbot-agent-nexus 模块设计

## 概述
Nexus — Agent 组件的编排中心。智能体的"思考"部分：负责将外部输入与记忆加工为 LLM 可用的上下文、驱动回复生成与工具调用，并统一调度同进程内的 Station、channel 适配层与记忆系统。Nexus 本身不实现 agentic loop 的执行步骤，而是由 pipeline 体系（输入处理 / 消息发送 / 工具调用 / 输出处理 / 系统提示词）组合出每个会话的执行流程，Nexus 向它们提供会话、记忆、Provider、Station 与回复发送能力。

Nexus 是 Agent 组件的一部分，与消息通道建立实时连接进行消息收发，与 memory-store、memory-ego 和 station 通过请求-响应方式通信。一个系统内可运行多个 agent 实例，每个实例独立的 Nexus 与 Station 单例。

一个 nexus 可同时管理多个会话。nexus 按每个绑定 channel 的 agent_id（空/缺省 = 保留 agent "0"）、role_name、mode 将所有绑定项去重，每个 agent_id+role_name+mode 组合为一个会话；各会话拥有独立的 LLM 上下文、记忆读写范围、pipeline 配置与模式状态。会话的回复目标由 (agent, role) 级 out_channel 配置决定（未配置 = 只存不回复），而不取决于消息从哪个 channel 到达。

## 核心功能

### Epic 1：外部输入处理
- **目标**：接收来自消息通道的输入，按消息来源 channel 的绑定配置定位会话，区分并路由管理命令与普通消息到对应处理流程
- **依赖**：Epic 5（消息通道通信）
- **用户故事**：
  - 作为一个用户，我要向智能体发送消息，以丢弃智能体自身发出后又回显的消息
  - 作为一个管理员，我要向智能体发送管理命令，以让智能体执行相应管理操作（无权限用户发送的命令被忽略）
  - 作为一个用户，我要向智能体发送普通消息，以触发智能体生成 LLM 回复

### Epic 2：LLM 交互
- **目标**：封装 LLM API 调用，支持多种 LLM 提供商和模型，构建完整的 LLM 上下文并调用
- **依赖**：Epic 3（上下文管理）、memory-ego（自我认知信息）
- **用户故事**：
  - 作为一个管理员，我要按 provider + model 配置 LLM 地址、密钥与参数，以控制 LLM 的行为
  - 作为一个管理员，我要为不同 (agent, role) 甚至单个会话指定不同的 provider/model 与参数
  - 作为一个管理员，我要配置 LLM 调用失败时的重试策略，以提高请求成功率
  - 作为一个用户，我要向智能体发送消息，以获取智能体调用 LLM 生成的回复，并让智能体将回复发送到消息通道

### Epic 3：上下文管理
- **目标**：按会话管理 LLM 上下文，支持恢复、增量追加与超长自动压缩/回溯
- **依赖**：Epic 4（记忆读写）、memory-ego（自我认知信息）
- **用户故事**：
  - 作为一个管理员，我要启动智能体程序，以让智能体按会话恢复上一次的本地上下文
  - 作为一个用户，我要向智能体发送消息，以让智能体保持对话连续性
  - 作为一个管理员，我要设置上下文 token 占用上限与压缩阈值，以防止上下文无限增长

### Epic 4：记忆读写
- **目标**：在会话创建时恢复本地上下文；在上下文超长时按配置压缩或从 memory-store 回溯打包；在 agentic loop 中把思考、tool call、tool result 与收发消息写入记忆系统；各会话按自身模式（角色/事件）隔离记忆范围
- **依赖**：memory-store（记忆读写）、memory-ego（自我认知信息）
- **用户故事**：
  - 作为一个用户，我要询问智能体过往的对话内容，以让智能体回顾对话脉络
  - 作为一个管理员，我要修改通道绑定的角色或记忆模式，以让智能体按模式隔离记忆范围
  - 作为一个用户，我要向智能体发送消息，以持久化智能体的思考过程和工具调用记录
  - 作为一个用户，我要向智能体发送消息，以持久化完整的对话收发记录

### Epic 5：消息通道通信
- **目标**：作为客户端连接消息通道的服务端，支持多通道同时连接、心跳检测和断线重连
- **依赖**：kissbot-channel（消息通道服务端与绑定协议）
- **用户故事**：
  - 作为一个管理员，我要配置通道绑定（每项含 channel 身份与 agent_id、role_name、mode），以让智能体启动时连接配置的通道并绑定用户
  - 作为一个外部系统（消息通道），我要与智能体保持长连接，以保持通信的稳定性
  - 作为一个外部系统（消息通道），我要向智能体推送上行消息并接收其下行消息

### Epic 6：工具调用分派
- **目标**：解析 LLM 返回中的 tool call，按工具名路由到全局 Station 执行（本级原生工具进程内执行 / 直接子 Station 经 MCP 递归）
- **依赖**：Epic 2（LLM 交互）、Station 组件
- **用户故事**：
  - 作为一个用户，我要向智能体提出需要执行工具的任务，以触发智能体执行工具调用
  - 作为一个外部系统（工具执行站），我要接收智能体发送的工具调用请求，以执行外置工具并返回工具执行结果
  - 作为一个用户，我要向智能体提出复杂的多步任务，以完成复杂的工具链调用

## 内部模块

### 1. 协调器（Nexus）
- 核心调度层：管理 nexus 的启动流程、会话集合与全局单例装配
- 按消息来源 channel 的绑定配置定位会话，将输入路由到管理命令处理或该会话的 pipeline
- 装配会话 pipeline 时注入会话实例（会话由 Nexus 创建），运行期 pipeline 直接读写会话上下文
- 提供能力接口供 pipeline 回调：Provider 调用、Station 工具分组白名单与调用、记忆写入（思考 / tool call / tool result）、记忆回溯打包、回复发送、ego 系统提示词查询
- 会话绑定（agent_id / role_name / mode）变更走串行队列，避免写-写竞态

### 2. 配置管理器
- 从公共配置加载静态配置（数据目录、监听地址、外部服务地址），引导并持久化 nexus.json / station.json
- 管理 provider+model 参数、(agent, role) 级会话配置（LLM 参数、压缩、记忆回溯、合批、回复通道、工具分组白名单、pipeline）与 session 级覆盖
- 运行期按 agent → role → session 逐层合成有效配置（带缓存），支持管理命令与管理 API 回写

### 3. LLM 客户端（provider 体系）
- 按 provider 配置的 provider_type 分派实现（OpenAI 兼容 / Anthropic），封装请求构造、调用、重试与响应归一化
- 归一化结果包含正文、思考内容（API 字段与 `<think>` 标签各自独立）、工具调用与 token 占用，供上下文与阈值判定使用
- 支持模型列表查询（用于模型校验与管理命令）

### 4. 会话与上下文（session_manager）
- 会话按 (agent_id, role_name, mode) 去重创建，返回「会话 + 是否新建」；仅负责上下文本体，不做 pipeline 装配
- 每会话持有 SessionContext（内存消息序列 + 当前/待定 system 消息），消息变更同步写入本地缓存，被压缩或重建前的上下文归档为历史
- 历史与缓存内容构成一致；恢复时正序全量回读，并做崩溃一致性清理（丢弃悬挂的 tool_calls 尾部与开头的孤立工具响应）

### 5. pipeline 体系（会话执行流程）
- **AgentPipeline**：agentic loop 本体，装配时注入会话实例，按轮次执行「发送 → 输出处理」，直至无需继续或达到轮次上限；结束轮次后把本轮新消息写回会话上下文
- **输入处理器（AgentInputProcessor）**：会话消息入口。默认实现为合批处理器——连续到达的消息先入队并刷新合批截止时间，到期后打包为一条 user 消息并请求启动该会话的 pipeline
- **消息发送器（AgentMessageSender）**：直接读写会话上下文并调用 LLM，返回归一化响应。默认实现三种：raw（直接发送）、compress（超阈值时 LLM 总结压缩上下文）、memory_recover（超阈值时从 memory-store 回溯打包重建上下文）；阈值判定所需的上次 token 占用由发送器自身维护
- **工具调用器（AgentToolCaller）**：执行单个 tool call 并回填结果，默认实现经适配层分派到全局 Station（把 Nexus 侧工具调用结构转换为 Station 的工具接口，再把结果还原回 Nexus 侧结构）
- **输出处理器（AgentOutputProcessor）**：构造本轮要回写上下文的消息（助手消息 + 工具结果消息）、判断是否继续下一轮、在有正文时经回复通道发送
- **系统提示词器（AgentSystemPrompter）**：持有会话，直接设置该系统消息；默认实现为固定提示词，另一实现从 memory-ego 读取自我认知信息（保留 agent 或读取失败时回退默认提示词）
- **trigger 标记（AgentTrigger）**：会话内可能与 pipeline 联动、且可保留多个实例的执行体统一标记（输入处理器与系统提示词器均实现它）；对应的 trigger 集合用于承载「无手动触发」的执行体（如定时 / 事件驱动），当前为空，尚无生产实现
- **PipelineManager**：按会话 key 持有 SessionPipeline（输入处理器 / 系统提示词器 / trigger 为按名索引的多实例集合，正在运行的 pipeline 由独立锁保护），提供装配（同步）、消息投递、系统提示词重置与随会话清理

### 6. 记忆读写
- 上行消息、下行回复、思考内容、tool call / tool result 统一经 memory-store 客户端写入；写入失败仅记录日志、不重试
- 上下文超长时的回溯读取由 memory_recover 消息发送器触发：按 (agent_id, role_name) 两次查询并集（最近 N 条 ∪ 时间段）打包为交替的对话消息，归档旧上下文后重建
- 首次合成会话配置时也读取记忆回溯配置（时间窗、条数），与 LLM 参数独立

### 7. 管理命令路由器
- 识别以 `/` 开头的外部消息（且发送者在来源 channel 的 admins 中）
- 解析并执行：绑定/解绑通道用户、管理权限增删、切换 agent/role、切换模式、设置/清除回复通道、切换会话模型
- 命令与命令回复不入记忆、不进会话上下文

### 8. 会话管理器
- 汇总所有绑定 channel 的 (agent_id, role_name, mode) 并去重，维护会话集合；按消息来源 channel 定位会话
- 绑定信息变化时清理无绑定会话（连同其 pipeline 与合批任务）
- 维护各 channel 的运行态 mode（默认角色模式，不回写配置）；事件模式会话按事件标识隔离上下文与记忆

### 9. Station 运行态
- 全局 Station 单例（每 agent 一个）从配置构建：本级 group 集合（工具元数据 + 原生实现，由内置注册表按 group 名填充）+ 直接子 Station 集合（仅连接信息，MCP 客户端）
- 内置示例工具 Read：读取文本文件，路径经绝对路径规范化后校验位于当前工作目录内（防穿透），返回内容限长；配置显式声明 filesystem group 名才注册
- 工具名 group 内唯一；本级构建时的重名静默保留先到者，级联合并时的跨子站重名保留先到者并记 warn 日志（对外仍给出唯一名字）

### 10. Station 工具执行
- 工具定义由 nexus 按会话的工具分组白名单聚合（平铺递归），并在边界处转换为 LLM 侧工具定义，随 LLM 请求发送
- 本级工具：按工具名在本级工具索引中查找并执行（注册的工具必带原生实现）；子 Station 工具：本级未命中时按工具名路由到归属的直接子 Station，经 MCP 调用（不遍历全部子）

### 11. 边界组件（非 Nexus 内部模块）
- **通道适配层（channel_manager）**：实现 Terminal（回显过滤 + 转发业务）、每 channel 运行态（pending msg_id、mode、client、断线通知）、连接/重连/发送，并持有 channel 变更串行队列（其执行体之一即会话重定位，回调 Nexus）
- **管理 API（http_server）**：管理界面用的配置 CRUD，直接操作配置管理器
- **station MCP 服务端（station_http）**：把全局 Station 作为 MCP 处理器对外提供 server/discover、tools/list、tools/call，供其他 station 作为 sub 使用

## 功能流程

### Epic 1 外部输入处理流程

```
通道适配层收到消息
  → 按 msg_id 查所属 channel 的未回显 outgoing 集合
    ├─ 命中 → 识别为自身发出的消息回显，丢弃（发送时已写入记忆）
    └─ 未命中 → 转发 Nexus：
        → 记忆写入：推上行消息（is_self=0）
        → 管理命令（文本以 "/" 开头且在 admins 中）→ 命令路由器执行 → 回复发回来源通道
        → 系统事件（群组变更 / 用户移除）→ 不进 pipeline
        → 普通消息 → 定位会话（按来源 channel 的绑定）→ 该会话的合批输入处理器
```

### pipeline 执行流程（agentic loop）

```
普通消息 → 合批输入（同一会话连续消息等待合批间隔后打包为一条 user 消息）
  → AgentPipeline：装配时注入会话（发送器 / 工具调用器 / 输出处理器，运行期直接读写该会话上下文）
  → 循环（上限防死循环）：
      1. 发送器：上下文超阈值时先压缩或记忆回溯 → 追加新消息 → 调用 LLM
      2. 输出处理器：
           ├─ 有 tool_calls → 逐个执行（全局 Station 经适配层）→ 结果作为工具消息追加 → 继续下一轮
           └─ 有正文 → 追加助手消息 → 经回复通道发送（并写入记忆）
  → 轮次结束：把本轮新增消息追加进会话上下文
```

### 启动流程

```
kissbot-agent 启动
  → 配置管理器：加载公共配置的 agent 段，引导 nexus.json / station.json
  → Station：读 station.json 构建全局单例（内置注册表 + 配置声明 + 唯一性校验 + 子 Station 连接信息）
  → Nexus：装配运行时组件并注册单例；同时启动 channel 变更队列消费者
  → 后台启动管理 API 服务与 station MCP 服务端
  → 主循环：对每个 channel 绑定确保会话存在（新建会话时同步 pipeline、设置系统提示词）
  → 主循环：连接全部 enabled channel（创建客户端 + 重连循环 + 绑定身份）
  → 保持进程，等待通道回调驱动
```

### 上下文超长处理流程

```
触发条件：本次请求前，上一次模型响应的 usage.total_tokens 超过
          会话模型 max_tokens_usage × 压缩阈值（max_tokens_usage = 0 表示不启用）
  → 该会话的消息发送器按配置执行一种处理：
    ├─ 压缩：追加压缩指令 → LLM 总结 → 归档当前上下文 → 重建为「压缩指令 + 总结」
    └─ 记忆回溯：从 memory-store 两次查询并集打包 → 归档清空 → 重建
  → 记录本次请求的 token 占用，供下次判定
```

### 事件模式流程

```
修改 channel 绑定为事件模式（/mode event）→ 会话管理器生成/指定事件标识，建立对应会话
  → 新会话按本地缓存恢复上下文（空则仅系统消息），记忆读写按「role-event」编码隔离
重新进入指定事件（/mode event <event-id>）→ 切回该事件会话，从该会话缓存恢复
回到角色模式（/mode role）→ 消息进入角色模式会话
```

## 关键设计

### 会话定义与记忆模式隔离规则

- 会话由（agent_id、role_name、mode）唯一标识；nexus 将所有绑定 channel 的信息去重生成会话集合，多个绑定相同三元组的 channel 共享同一会话
- 记忆读写用 agent_id 直接定位（配置即 agent_id，无需二次解析），role 编码 = 角色名（角色模式）或「角色名-事件 ID」（事件模式）
- 角色模式会话：记忆读写覆盖该角色下所有记录；事件模式会话：只覆盖本事件的记录
- 绑定信息变化产生新会话时重新恢复/构建上下文

### 回复通道

- 回复目标由 (agent, role) 级 out_channel 配置决定，经 `/bind-outgoing` 设置、`/unbind-outgoing` 清除；未配置 = 只存不回复
- 发送前校验该身份仍在目标 channel 的绑定集合中；已解绑（配置悬空）则清理配置并跳过发送

### 管理命令说明

| 命令类别 | 用途 |
|---------|------|
| 绑定/解绑 | 绑定或解绑指定通道的用户 |
| 管理权限管理 | 添加或移除用户的管理权限 |
| agent/角色切换 | 修改指定通道绑定的 agent 与角色 |
| 模式切换 | 修改指定通道绑定的记忆模式（角色/事件） |
| 回复通道 | 设置或清除 (agent, role) 的回复通道 |
| 模型切换 | 切换当前会话使用的 provider/model（校验后生效） |

### 自身发送消息识别

- agent 自己发出的消息（下行）经通道回显时，其 msg_id 与发送时响应返回的 msg_id 一致
- 发送成功后把返回的 msg_id 记入对应 channel 的未回显集合（TTL 懒清理）
- 收到消息时按 msg_id 查该集合：命中则移除并丢弃（发送时已写入记忆）；未命中则视为普通上行消息写入记忆（is_self=0）

### 自动上下文处理

最近一次模型响应的 token 占用超过「会话模型上限 × 压缩阈值」时，下次请求前由消息发送器触发处理：压缩（LLM 总结后重建上下文）或记忆回溯（从 memory-store 打包重建），随后更新占用记录，防止上下文无限增长。阈值为 0（或上限为 0）时不启用该机制。

### 初始上下文构建

- 会话创建时从本地缓存全量恢复（缓存生命周期 = 当前上下文，超长即压缩，天然有界），不读取记忆
- 系统消息由系统提示词器设置（固定提示词 / memory-ego 自我认知 markdown），先存为待定，发送前对比应用；系统消息随消息一并持久化，恢复时回到当前系统消息
- 运行时每次收到合批后的用户消息和 LLM 回复（含工具调用与结果）后增量追加到该会话的上下文并同步写入缓存
- 运行时每次收到合批后的用户消息和 LLM 回复（含工具调用与结果）后增量追加到该会话的上下文并同步写入缓存

### 记忆写入

- 上行消息（is_self=0）、下行回复（is_self=1，内容取发送响应）、思考内容（reasoning_content / thinking 任一有值）、tool call 与 tool result（同一 UUID key 关联）统一写入 memory-store
- 写入失败仅记录日志、不重试，避免阻塞后续操作

### 通道连接管理

- 启动时按配置中的 enabled channel 建立连接，连接后按 bind_users 逐个绑定身份；每个连接独立运行，支持心跳与断线自动重连
- 上行消息按来源 channel 定位会话后送入该会话的 pipeline；下行消息经会话的回复通道发送，并记录未回显 msg_id

### 工具调用分派

- LLM 返回 tool call 时解析工具名与参数
- 工具定义按会话的工具分组白名单聚合（平铺递归），转换为 LLM 侧工具定义后随每次 LLM 请求发送
- 工具调用按工具名路由：本级原生实现在进程内执行，未命中查工具路由（工具名 → 直接子 station_id）经 MCP 调对应子；路由未命中返回错误结果
- 工具结果作为工具消息追加回上下文，支持多轮嵌套（上限防死循环）
- 每个工具调用生成 UUID key，相关记忆记录用同一 key 关联，经通道时间线可见工具调用锚点

### LLM 调用重试

- LLM 调用失败时按 provider/model 配置的重试次数与超时自动重试（指数退避），提高请求成功率
