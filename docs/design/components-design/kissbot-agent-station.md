# kissbot-agent-station 模块设计

## 概述

Station — Agent 组件的 Tool 执行主机模块。智能体的"行动"部分，专注于执行具体的工具操作。Station 不直接与 LLM 通信，只提供工具注册、接收工具调用、执行工具、将结果返回给 Nexus 的能力。

Station 同时具有 **MCP 服务端**与 **MCP 客户端**双重角色：
- 作为 MCP 服务端，对外提供工具发现与工具调用能力，可被上级 Station 或其他 MCP 客户端调用
- 作为 MCP 客户端，经 MCP 调用直接子 Station，把整棵 Station 树的工具聚合到本级

Station 采用**嵌套结构**：
- **全局单例**：每个 agent 进程内只有一个全局 Station，启动时从配置构建
- **两级节点**：Station 内部由两层组成——本级 **group 集合**（每组含工具元数据与可选的本地实现）与直接**子 Station 集合**（仅连接信息，经 MCP 通信）
- **子 Station 仅 MCP**：子 Station 只能通过 MCP 与父通信；父只存直接子连接信息，孙子由子 Station 进程自己递归，父不管
- **station 自身也是服务端**：每个 station 监听独立配置的对外端点，可被其他 station 当作 sub 调用
- **配置落盘**：Station 配置由 ConfigManager 承载，可修改并持久化

Station 可以运行在多种形态的设备上：
- **通用服务器**：运行标准工具集（文件操作、命令执行等）
- **网络设备**：读写网络配置、获取监控数据等
- **智能家电**：执行物理世界操作（开关、调节等）
- **机器人**：执行物理动作（移动、抓取等）

## 核心功能

### Epic 1：工具注册与分组
- **目标**：按配置声明启用哪些工具分组，由内置注册表成对填充工具元数据与原生实现，并保证工具名在本级唯一
- **依赖**：kissbot-mcp（工具定义与结果结构）、配置管理器
- **用户故事**：
  - 作为一个管理员，我要在配置中声明启用哪些工具分组，以圈定本级对外提供的工具范围
  - 作为一个外部系统（工具实现方），我要为本级原生工具提供实现，以让智能体在本地执行该工具
  - 作为一个管理员，我要在声明内置分组后直接获得内置工具，以使用常用能力

### Epic 2：MCP 服务端
- **目标**：对外提供 MCP 服务（服务发现、工具列表、工具调用），并沿用统一的调用约定
- **依赖**：Epic 1（工具注册与分组）、kissbot-mcp
- **用户故事**：
  - 作为一个外部系统（上级 Station），我要把 Station 当作 MCP 服务端调用，以复用其工具能力
  - 作为一个外部系统（MCP 客户端），我要查询 Station 的工具定义，以把工具交给语言模型选择调用
  - 作为一个管理员，我要限制 Station 的外部访问，以控制能力暴露范围

### Epic 3：子 Station 客户端与级联
- **目标**：把直接子 Station 作为 MCP 服务端接入，递归聚合与路由工具，在级联时检测循环调用，并兼容不理解 kissbot 扩展的第三方 MCP 服务端
- **依赖**：Epic 2（子 Station 自身是 MCP 服务端）、kissbot-mcp
- **用户故事**：
  - 作为一个管理员，我要把多个 Station 组织为树形结构，以组合多台设备上的工具
  - 作为一个外部系统（上级 Station），我要级联查询下级 Station 的工具，以使用下级设备上的工具
  - 作为一个外部系统（上级 Station），我要在级联时携带祖先链，以避免循环调用
  - 作为一个管理员，我要把第三方 MCP 服务端挂为本级子节点，以在不改造对方的前提下复用其工具
  - 作为一个管理员，我要为子节点指定默认分组，以让第三方 MCP 服务端的工具也能被分组白名单圈定

### Epic 4：工具发现与分组过滤
- **目标**：聚合本级与直接子 Station 的工具定义，按分组白名单过滤，并让每个工具都带上所属分组
- **依赖**：Epic 1（工具注册与分组）、Epic 3（子 Station 客户端与级联）
- **用户故事**：
  - 作为一个外部系统（MCP 客户端），我要按分组过滤工具定义，以只获取本次任务需要的工具
  - 作为一个管理员，我要为不同会话启用不同的工具分组，以控制智能体可用的工具范围

### Epic 5：工具执行
- **目标**：按工具名在本级原生实现与直接子 Station 之间路由并执行工具，回填成功结果或失败错误
- **依赖**：Epic 1（工具注册与分组）、Epic 3（子 Station 客户端与级联）
- **用户故事**：
  - 作为一个用户，我要让智能体执行工具任务，以完成具体的操作
  - 作为一个外部系统（MCP 客户端），我要调用 Station 的工具，以获得工具执行结果
  - 作为一个用户，我要让智能体使用下级 Station 上的工具，以完成需要其他设备参与的任务

## 模块划分

- **NativeTool**：本级原生工具接口，统一入参（JSON 参数）与出参（MCP 工具结果）
- **Station**：全局单例，持有 station_id、本级 group 集合、直接子 Station 集合与工具路由信息；实现 MCP 服务端处理器
- **Group**：一组工具（工具元数据 + 原生实现，注册的工具必须可执行），组名在本级内唯一
- **SubStation**：直接子 Station 运行态，只存连接信息与 MCP 客户端
- **内置注册表**：内置 group 的工具元数据与原生实现（当前为 filesystem 的 read）
- **station_http**：把全局 Station 接入 MCP 服务端并监听对外端点；认证由安全组件以中间件叠加

## 功能流程

### 工具元数据查询（MCP tools/list 平铺）
```
收到 MCP tools/list 请求（可带 group 白名单与祖先链）
  → 自身 station_id 已在祖先链中 → 返回协议级循环错误
  → 本级：按 group 白名单过滤 group，收集命中 group 的工具定义与 group 名
  → 直接子节点：判定其是否支持 kissbot 分组扩展（首次经服务发现判定并缓存）
      ├─ 支持 → 以同一 group 白名单与祖先链（追加自身 station_id）经 MCP 查询，按工具携带的分组归因
      └─ 不支持 → 不带分组查询，其工具归入该子节点的默认分组，再由本级按白名单在本地过滤
      ├─ 成功 → 合并工具定义，并使本级可按工具名路由到该子节点
      └─ 失败 → 记录告警跳过（保留该子上一次查询得到的工具归属）
  → 汇总工具定义与命中分组
  → 返回工具定义（每个工具携带自身分组）
```

### 工具调用流程
```
收到 MCP tools/call 请求（工具名 + 参数 + 祖先链）
  → 自身 station_id 已在祖先链中 → 返回协议级循环错误
  → 本级工具表命中：
      ├─ 有原生实现 → 执行并返回结果
  → 本级未命中 → 按工具名找到归属的直接子 Station，经 MCP 转发调用（祖先链追加自身 station_id）
      ├─ 子调用失败 → 返回外部错误结果
      └─ 成功 → 返回子 Station 的结果
  → 仍未命中 → 返回"工具不存在"
```

### 服务发现流程
```
收到 MCP server/discover 请求
  → 返回工具能力、协议版本、服务端身份与使用说明
```

### Station 启动流程
```
kissbot-agent 启动
  → ConfigManager（加载 agent 配置，引导 nexus/station 持久化配置）
  → Station（读配置 → 内置注册表填充 + 配置声明补充 + 工具名唯一性校验 + 子 Station 连接信息 → 注册全局单例）
  → Nexus（装配 + 注册单例）
  → StationHttpServer（后台启动 Station 的 MCP 服务端）
```

## 关键设计

### 工具名整树唯一
工具名在本级为硬约束，构建时对全部 group 去重，重名（含与内置实现同名）启动失败；跨进程部分在聚合子 Station 工具时处理——与本级或先到子重名的工具保留先到者，后到者剔除并记录告警。工具名整树唯一是工具路由的前提：任一工具名至多对应一处实现。

### 分组白名单
会话启用哪些 group 由会话配置决定，为空即无工具。对声明支持 kissbot 扩展的子节点，分组白名单同时下传，保证整棵树按同一范围过滤；每个工具都携带所属分组（子节点未携带时回落该子节点的默认分组），便于调用方归因。

### 兼容第三方 MCP 服务端
子节点不要求是 kissbot Station。本级在首次接触时经服务发现判定对端是否声明 kissbot 扩展，并缓存判定结果：声明支持则下传分组白名单并采信工具携带的分组；未声明则不下传分组，而是把该子节点的全部工具归入其配置的默认分组，由本级按白名单在本地过滤。这样标准 MCP 服务端无需任何改造即可作为子节点接入，同时仍能被分组机制圈定。

### 内置 filesystem 分组
配置显式声明该分组时才注册 read 工具。read 读取文本文件，路径经绝对路径规范化后校验位于进程工作目录内（防路径穿透），返回内容限长。

### 与 Nexus 的边界
Station 对外只使用 MCP 工具类型；Nexus 侧的工具调用与结果结构属于 Nexus 交互层，由 pipeline 的工具调用器在边界处完成转换，Station 内部不感知该结构。转换只取 MCP 的 `content`：成功作为结果、失败作为错误，内容块数组完整保留（文本、图片、音频、资源链接、嵌入资源）；`structuredContent` 仅用于 Station 内部处理，不进入 Nexus。进入 LLM 上下文前渲染为文本（文本块取原文，二进制内容给紧凑占位）。

### 级联防环
级联查询与级联调用都携带祖先链（根到当前父节点的站点标识链）；任一层发现自身站点标识已在链中即拒绝，避免 Station 树出现环导致的无限递归。

### 子 Station 只存连接信息
父 Station 只保存直接子 Station 的连接信息与 MCP 客户端，不感知子 Station 内部结构；孙子由子 Station 进程自己递归。子 Station 的连接失败只影响该子，不阻断本级与其他子的查询。
