# kissbot-api 组件设计

## 概述

API 定义库是组件之间数据交换的契约层。它以程序库形式被其他组件引用，定义统一的响应格式、公共网络地址配置、跨组件共享的基础类型，以及各组件通信所需的请求与响应数据类型。组件之间实际传输的数据结构以本库为准，通信双方因此不需要各自维护一份重复的定义。

## 核心功能

### Epic 1：统一响应与通用约定

- **目标**：定义所有 HTTP 接口共用的响应格式，以及配置继承、字段访问等跨组件通用的约定
- **依赖**：无
- **用户故事**：
  - 作为一个外部系统（服务端组件），我要用统一的响应结构包装返回结果，以让调用方以同一种方式判断成功与失败
  - 作为一个外部系统（调用方组件），我要按统一结构解析响应，以用同一段代码处理所有组件的返回
  - 作为一个外部系统（组件），我要复用配置合并与字段访问的通用约定，以在不同组件中保持一致的配置处理方式

### Epic 2：公共网络地址配置

- **目标**：定义各服务对外地址的配置结构，并支持从公共配置中读取
- **依赖**：kissbot-config（公共配置加载）
- **用户故事**：
  - 作为一个外部系统（agent），我要读取记忆存储、自我认知与摘要记忆的服务地址，以访问这些服务
  - 作为一个管理员，我要在一处配置中维护所有跨进程地址，以统一调整部署

### Epic 3：消息与通道类型

- **目标**：定义通道通信使用的消息内容模型、消息方向、通道身份与群组/用户变化通知
- **依赖**：无
- **用户故事**：
  - 作为一个外部系统（通道实现），我要用统一的内容类型表达文本、附件、复合消息与系统消息，以让同一条消息可以包含多种内容
  - 作为一个外部系统（agent），我要按统一的内容类型解析上行消息、构造下行消息，以不依赖具体通道实现
  - 作为一个外部系统（通道客户端），我要使用统一的通道身份与绑定结构，以与任意通道服务端对接

### Epic 4：记忆与摘要记忆类型

- **目标**：定义记忆范围、通道记录、记录元信息、查询条件，以及摘要记忆的 case 查询、定位与重建类型
- **依赖**：Epic 3（消息与通道类型）
- **用户故事**：
  - 作为一个外部系统（agent），我要用统一的记忆范围表达角色记忆与事件记忆，以让记忆组件无需了解业务语义
  - 作为一个外部系统（记忆存储），我要按统一结构接收通道记录与查询条件，以向所有调用方提供一致的行为
  - 作为一个外部系统（摘要记忆），我要按统一结构接收定位与查询请求，以向 agent 与记忆管理界面提供一致的能力

### Epic 5：自我认知与工具类型

- **目标**：定义自我认知的数据模型（agent 元数据、个体识别、角色设定），以及工具结果使用的内容块与工具调用结构
- **依赖**：无
- **用户故事**：
  - 作为一个外部系统（agent），我要按统一结构读取自我认知信息，以构建系统提示词
  - 作为一个外部系统（自我认知服务），我要按统一结构接收读写请求，以向界面与 agent 提供一致的数据视图
  - 作为一个外部系统（agent），我要用统一的内容块结构承载工具结果，以在模型上下文中渲染文本、图片、资源等内容

## 模块划分

- **通用模块**：统一响应格式、共享容器的通用工具、配置合并与字段访问约定
- **网络地址配置**：跨进程服务地址的配置结构
- **消息模块**：消息内容类型、附件信息、群组与用户变化通知
- **通道模块**：通道身份、通道信息、绑定与收发消息、附件下载请求与数据包结构
- **记忆模块**：记忆范围、通道记录、记录内容（思考、工具调用、工具结果）、记录元信息、查询与通知类型
- **摘要记忆模块**：case 节点、定位、case 查询与分页、树查询、重建的请求与响应类型
- **自我认知模块**：agent 元数据、个体识别、角色设定及其读写请求类型
- **工具模块**：工具结果使用的内容块与资源内容类型

## 功能流程

```
组件需要跨进程通信
  → 从本库引用对应的请求/响应类型（不存在则在本库新增）
  → 发送方按类型构造请求，接收方按同一类型解析
  → 服务端把结果包装为统一响应结构返回
  → 调用方按统一响应结构判断成功、失败并取出数据
```

## 关键设计

### 单一契约来源

同一个数据结构只在契约库中定义一次，通信双方共享同一份定义。这样字段变更只有一处需要修改，也不会出现两端定义漂移。

### 基础类型与业务类型分层

消息内容、通道身份、记忆范围这类跨组件基础类型与各组件专属的请求/响应类型放在同一库中，但按模块分开：基础类型被多个组件共同引用，专属类型只服务于对应组件的通信。

### 配置继承约定

配置的逐级覆盖与「可继承配置 → 有效配置」的合成方式以通用约定的形式定义，各组件按同一套方式实现自己的配置类型，从而在 agent 的 agent/角色/会话分级、模型参数合成等场景中保持一致语义。

### 容器类型直接序列化

共享引用类型直接参与序列化，调用方不需要为传输做额外的结构转换；同时保持与运行时一致的类型，避免在同一份数据上维护两套表示。
