# kissbot-channel-web 组件设计

## 概述

Web 通道是消息通道的一个完整实现：它既实现 Messenger 接口（作为通道实现接入框架），又自带通信工具本身——管理员通过 Web 界面使用，普通用户由 agent 以通道客户端身份接入。组件包含后端服务（通道实现、消息与附件存储、管理接口、实时推送）和前端应用（管理员界面）。

与只作为对接层的通道实现不同，它保存历史消息与附件，因此具备完整的聊天工具能力。

## 核心功能

### Epic 1：用户与群组模型

- **目标**：维护管理员、普通用户与群组三类实体，以及管理员与每个用户之间的单聊
- **依赖**：kissbot-channel（Messenger 接口与通道服务端）、kissbot-security（密钥）
- **用户故事**：
  - 作为一个管理员，我要新建普通用户，以作为 agent 的身份接入通道
  - 作为一个管理员，我要重命名或删除用户，以维护用户列表
  - 作为一个管理员，我要新建群组并选择成员，以组织多人会话
  - 作为一个管理员，我要重命名群组、增减成员或删除群组，以调整会话组织
  - 作为一个管理员，我要与某个用户单聊，以一对一地使用智能体

### Epic 2：消息收发与分发

- **目标**：接收管理员与 agent 发送的消息，生成消息标识与时间，并在消息落盘后推送给相关方
- **依赖**：Epic 1、Epic 4（附件）
- **用户故事**：
  - 作为一个管理员，我要在界面上向某个会话发送文本或附件，以与 agent 对话
  - 作为一个外部系统（agent），我要收到绑定身份所在群组的上行消息，以处理用户输入
  - 作为一个外部系统（agent），我要把回复发送到指定群组，以让对应成员收到
  - 作为一个管理员，我要在不刷新页面的情况下看到新消息，以持续对话

### Epic 3：消息持久化与翻阅

- **目标**：把消息按群组与日期持久化，支持最近消息、向上翻阅与按位置定位
- **依赖**：Epic 1、Epic 2
- **用户故事**：
  - 作为一个管理员，我要重新进入会话时看到最近的聊天记录，以继续此前的对话
  - 作为一个管理员，我要向上滚动加载更早的消息，以回顾历史
  - 作为一个管理员，我要按时间定位到某条消息，以查看它前后的内容
  - 作为一个管理员，我要在消息落盘后仍能查询到它，以确认记录完整

### Epic 4：附件存储与访问

- **目标**：保存消息附件的本体、元数据与缩略图，提供上传、下载与缩略图访问
- **依赖**：Epic 1
- **用户故事**：
  - 作为一个管理员，我要上传图片，以在会话中发送图片并看到缩略图
  - 作为一个管理员，我要上传文件，以在会话中发送可下载的附件
  - 作为一个管理员，我要点击缩略图查看原图，以看清图片细节
  - 作为一个管理员，我要下载附件本体，以取得文件

### Epic 5：管理接口与实时推送

- **目标**：为管理员界面提供管理接口与服务端推送，使界面能完成会话管理、消息发送与实时接收
- **依赖**：Epic 1~4、kissbot-security（管理密钥）
- **用户故事**：
  - 作为一个管理员，我要在界面选择后端并输入管理员密钥，以连接到某个 Web 通道
  - 作为一个管理员，我要看到会话列表与未读数，以知道哪里有新消息
  - 作为一个管理员，我要管理群组与用户，以维护会话组织
  - 作为一个管理员，我要在连接断开后自动恢复推送，以不丢失后续消息

## 模块划分

- **配置与仓库**：加载组件配置；维护可写的用户与群组仓库（含序号分配），修改后整份写回文件
- **用户与群组管理**：用户与群组的增删改、群组成员维护、单聊群的派生，以及对应的通道事件上报
- **消息存储**：按群组与日期组织消息文件，落盘后重写时间、更新可查询日期并触发推送
- **附件存储**：附件本体、元数据与缩略图文件，上传处理与缩略图生成，按存储标识访问
- **通道服务端接入**：以 Messenger 实现注册到通道服务端，处理收发消息、群组与用户事件、附件分块
- **管理接口**：面向管理员界面的 HTTP 接口（会话信息、收发消息、历史翻阅、群组与用户管理、附件上传下载）
- **实时推送**：向管理员界面广播落盘后的消息
- **前端应用**：登录与后端选择、会话列表、消息区、群组管理面板、用户管理面板

## 功能流程

### 发送与分发流程

```
收到发送请求（管理员或 agent）
  → 校验发送者权限与目标群组
  → 注册附件（若有），得到存储标识与传输标识
  → 分配消息标识与时间，按发送时间确定日期文件
  → 交给写入流程：消息进入写入流程后即返回成功
  → 落盘时：重写这批消息的时间 → 更新可查询的日期集合 → 使该文件的查询索引失效
  → 先向管理员界面广播消息，再按当时的群组成员向各用户连接分发
```

### 上行消息流程

```
用户的连接（agent）在群组中收到消息时
  → 按群组成员确定接收者，逐个推送给其绑定的连接
  → 单聊群：管理员发送时推给该用户；用户发送时回显给该用户自己
  → 管理员不参与用户连接的分发
```

### 消息翻阅流程

```
最近若干条：按日期集合从新到旧逐日取尾部，取满后按时间升序返回
以某条消息为锚点向前 / 向后取：从锚点所在文件开始，文件内不足时借日期集合跨文件补齐
按时间范围取：把区间切成按日段后逐文件读取
```

### 附件流程

```
上传：消息声明附件元信息 → 注册得到传输标识 → 按块写入临时文件
      → 收满声明大小后转为正式文件、生成缩略图、更新元数据
      → 下载：按存储标识读取元数据与本体，支持单段范围请求
      → 缩略图：图片按最长边等比缩放生成，非图片按错误处理
```

### 群组与用户事件流程

```
创建群组 / 增加成员 → 给新增成员上报「加入」事件
移除成员 / 删除群组 → 给被移除成员上报「退出」事件
删除用户 → 从所有群组成员中移除该用户，再上报「用户删除」事件
重命名群组或用户 → 只更新配置，不上报事件
```

## 前端功能流程

### 接入流程

```
加载后端列表（站点根目录下的静态配置文件，可直接替换而不重新构建）
  → 选择预置后端或输入自定义地址，输入管理员密钥
  → 连接成功：拉取通道信息，构造会话列表（后端群组 + 由用户派生的单聊）
  → 订阅消息推送
```

### 会话与消息流程

```
选中会话 → 加载最近若干条消息
  → 向上滚动接近顶部时加载更早的消息
  → 输入文本或选择附件后发送
  → 消息推送到达：归入对应会话的日期分组；不是当前会话则累加未读数
  → 打开某个会话时清零该会话的未读数
```

## 关键设计

### 管理员不是通道用户

管理员是操作员身份，不出现在通道的用户表中，因此 agent 无法绑定管理员、也无法向管理员身份发消息。管理员通过界面查看全部会话（包括自己不在其中的群组），但不能向自己不在的群组发送消息。这样「人类操作者」与「agent 身份」在模型上彻底分开。

### 单聊群由规则派生

每个用户都有一条与管理员的单聊，但单聊不写入群组仓库，而是按「单聊前缀 + 用户标识」在运行时派生；服务端、前端各自按同一规则构造。好处是不必为每个用户维护一条群组记录，也不会出现单聊与用户不一致的状态；代价是这条规则成为服务端与前端之间的隐式约定。

### 先入队后落盘，落盘后才推送

发送请求在消息进入写入流程后即返回成功，此时消息尚未落盘；真正的推送发生在落盘之后。这样发送方不必等待磁盘写入，而所有接收方看到的都是已经持久化的消息，不会出现「收到但查不到」的情况。

### 时间以落盘为准

消息时间在落盘时统一写入，而非发送时确定。若落盘时已经跨天，则把时间重写为该文件所属日期的最后一秒，保证文件内的消息时间与文件日期一致。这样按日期翻阅时不会出现「今天的文件里有昨天的消息」。

### 分发时按当前成员计算

消息落盘后按当时的群组成员分发，而非按发送时的成员。成员在发送与落盘之间发生变化时，以最新的成员关系为准，避免向已退出的成员继续推送。

### 附件三文件与转正

附件分为本体、元数据、缩略图三类文件；上传期间写入临时文件，收满数据后才转为正式文件。这样未完成的上传不会产生可用但残缺的附件；缩略图在转正时预生成，读取时复用已加载的元数据。

### 实时推送面向管理员界面

管理员界面使用服务端推送接收消息，而非长连接双向通信，以避免浏览器侧的连接管理复杂度。推送面向全部会话（管理员可以查看所有群组），界面按会话归类并计算未读。

### 界面状态保持在前端

会话列表、消息分组、翻页游标、已加载消息标识集合与未读数都由前端持有，后端只提供查询与推送。后端因此不需要为每个界面维护会话状态；刷新页面会重新从后端拉取。
