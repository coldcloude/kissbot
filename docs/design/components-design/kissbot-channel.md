# kissbot-channel 组件设计

## 概述

kissbot-channel 是消息通道框架，以程序库形式提供服务端能力与抽象接口。它定义 **Messenger** 接口，作为具体通信工具接入的标准；并实现通道服务端，作为通信工具与客户端（agent）之间的代理：对外接受客户端的长连接，管理连接与身份绑定，在通信工具与客户端之间转发消息与附件。

框架本身不保存消息，也不与记忆系统交互；历史消息由各通道实现自行决定如何保存。

## 核心功能

### Epic 1：客户端连接管理

- **目标**：作为服务端接受客户端的长连接，管理连接生命周期、心跳与断线清理
- **依赖**：kissbot-security（握手认证）
- **用户故事**：
  - 作为一个外部系统（agent），我要连接到通道服务端，以建立双向通信通道
  - 作为一个外部系统（agent），我要与通道服务端保持长连接，以及时发现断线
  - 作为一个管理员，我要限制未持有密钥的连接，以控制谁能接入
  - 作为一个外部系统（agent），我要在断线后重新连接并重新绑定，以恢复通信

### Epic 2：通道接入与通道信息

- **目标**：提供 Messenger 接口与注册机制，让通道实现接入；并向客户端提供通道、用户与群组信息
- **依赖**：无
- **用户故事**：
  - 作为一个外部系统（通道实现），我要实现 Messenger 接口并注册，以接入框架
  - 作为一个外部系统（agent），我要查询通道名称、用户列表与各用户的群组，以决定绑定哪些身份
  - 作为一个外部系统（agent），我要在通道信息变化后重新查询，以更新本地认知

### Epic 3：身份绑定

- **目标**：把客户端连接与通道上的用户身份绑定，作为消息路由的依据
- **依赖**：Epic 1、Epic 2
- **用户故事**：
  - 作为一个外部系统（agent），我要把连接绑定到某个用户身份，以开始接收该身份的消息
  - 作为一个外部系统（agent），我要在不需要时解绑，以停止接收该身份的消息
  - 作为一个管理员，我要让一个身份同一时刻只被一个连接绑定，以避免消息被重复投递

### Epic 4：消息路由与事件通知

- **目标**：把通道上报的上行消息推送给绑定该身份的连接，把客户端的下行消息交给通道实现发送；并转发群组变化与用户删除事件
- **依赖**：Epic 3
- **用户故事**：
  - 作为一个用户，我要在通信工具里发消息，以让绑定该身份的 agent 收到
  - 作为一个外部系统（agent），我要发送消息并取得消息标识与时间，以完成回复
  - 作为一个外部系统（agent），我要收到群组加入、退出与用户删除的通知，以更新自己的通道状态
  - 作为一个用户，我要在 agent 未连接时消息仍被通信工具保存，以不丢失记录

### Epic 5：附件传输

- **目标**：在客户端与通道实现之间传输附件，消息里只携带附件的存储标识与传输标识
- **依赖**：Epic 2、Epic 3、Epic 4
- **用户故事**：
  - 作为一个用户，我要发送附件，以让对方收到文件本体
  - 作为一个用户，我要下载附件，以取得文件内容
  - 作为一个外部系统（agent），我要在消息里只看到附件的标识与元信息，以按需再取数据
  - 作为一个外部系统（通道实现），我要按块接收和发送附件，以在不占用大量内存的前提下传输大文件

## 模块划分

- **Messenger 接口**：通道实现需提供的能力——读取通道与用户/群组信息、发送消息并返回消息标识与时间、写入上传分块、解析下载请求并分配传输标识、启动下载分块推送
- **通道服务端**：监听连接、维护连接表与绑定表、处理客户端的请求、向客户端推送事件、协调附件传输
- **附件注册与传输**：把消息中的附件元信息转换为「存储标识 + 传输标识」，维护上传与下载两条传输路由，组装与解析二进制分块
- **事件类型**：上行消息、群组加入/退出、用户删除等事件的数据形态

## 功能流程

### 连接与绑定流程

```
客户端建立连接（握手携带密钥）
  → 服务端校验密钥，分配连接标识并保存连接上下文
  → 客户端查询通道信息，选取要绑定的用户身份
  → 服务端校验该用户确实存在于通道实现的用户表中
  → 记录「该用户 → 本连接」，绑定成功
  → 连接关闭时移除连接，并清理指向该连接的全部绑定
```

### 下行消息流程

```
客户端发送下行消息（messenger、用户、群组、内容）
  → 校验连接已绑定该用户
  → 交给通道实现发送：分配消息标识与时间，并把附件注册成存储标识与传输标识
  → 框架递归遍历响应内容，登记每个附件的传输路由
  → 把响应返回客户端
```

### 上行消息流程

```
通道实现上报「接收者身份 + 消息」
  → 按接收者查绑定，找到对应连接
  → 以独立推送帧推送给客户端（携带接收者身份与完整消息）
  → 接收者未绑定：记录日志并丢弃（不排队、不补发）
```

### 群组与用户事件流程

```
通道实现上报群组加入
  → 先推送「加入」控制通知，再把事件作为系统消息推送
通道实现上报群组退出
  → 先把事件作为系统消息推送，再推送「退出」控制通知
通道实现上报用户删除
  → 先从绑定表移除该用户，再推送删除通知
```

### 附件上传流程

```
客户端在消息中携带附件元信息 → 服务端注册，返回存储标识与本次传输标识
  → 客户端按传输标识连续发送二进制分块（含分块位置与数据）
  → 服务端按传输标识找到通道实现并写入
  → 逐块把写入结果（当前进度、错误码）作为响应返回
  → 收满声明大小或写入失败后清理该传输路由
```

### 附件下载流程

```
客户端携带存储标识请求下载
  → 校验该用户绑定在本连接
  → 通道实现返回附件信息并为本次下载分配新的传输标识
  → 先返回下载头响应，再由通道实现逐块推送
  → 每推送一块等待客户端确认；确认失败或传输失败即停止
  → 传输结束或失败后清理该下载路由
```

## 关键设计

### 服务端作为代理

框架不直接面向外部通信工具，而是把通信工具抽象为 Messenger、把客户端抽象为连接。这样同一个通道服务端可以接入不同的通信工具，客户端也只需实现一套协议即可对接任意通道实现。

### 绑定是路由的唯一依据

消息按「接收者身份」路由，而非按发送者或群组。一个身份在同一时刻只被一个连接绑定，因此一条上行消息至多被投递一次。连接断开即失去全部绑定，重连后必须重新绑定。

### 上行不排队

上行消息只有在接收者已绑定时才被推送；未绑定时直接丢弃。通信工具端的消息已经保存，因此丢失的只是「实时投递」，而非消息本身；订阅方需要时通过历史查询补齐。

### 事件顺序编码语义

群组加入时先发控制通知再发系统消息，退出时先发系统消息再发控制通知。前者让客户端先建立对该群组的认知再看到系统消息，后者让客户端先看到系统消息再失去该群组。用户删除则先解绑再通知，避免通知到达时客户端仍能向该身份发消息。

### 附件的两阶段表示

消息里只携带附件的元信息；注册后转换为「存储标识 + 传输标识」。存储标识是附件的永久标识，传输标识只在本次传输中有效，用于把数据块路由到正确的通道实现与连接。二者分离使同一附件可以被多次独立传输，也避免把存储细节暴露在消息中。

### 传输是停止等待式

上传是「发一块、收一块响应」，下载是「发一块、等一块确认」。没有校验和、没有重传、没有断点续传；中断后只能重新发起传输。这样实现简单、顺序明确，代价是需要调用方配合纠正乱序与重试。

### 传输顺序由通道实现保证

框架只按声明的总大小判断上传是否完成，不纠正乱序；分块的顺序与幂等语义由各通道实现负责（例如落后块视为重复、超前块返回乱序错误）。下载的推送由通道实现驱动，框架只负责组帧、发送与等待确认。

### 不持久化

框架不保存消息、不保存绑定、不保存传输状态。因此它可以在进程重启后立即恢复使用（客户端重连并重新绑定即可），也不会成为消息可靠性的责任方。
