# kissbot-llm 组件设计

## 概述

kissbot-llm 是 kissbot 的 LLM 基础库（Rust lib），把「与模型服务商通信」和「会话上下文管理」从 agent 中抽出，供 agent 之外的模块复用（如摘要记忆系统、笔记工具等需要 LLM 的模块）。组件只做两件事：按调用方给出的 provider 配置完成一次模型调用，按调用方给出的会话标识管理 LLM 上下文。

组件刻意不含三类能力，以保持边界清晰：

- **不含会话集合管理**：会话的去重、持有与无绑定清理属调用方（agent 中为 SessionManager），组件只提供单个会话的上下文。
- **不含配置存储与继承链**：provider 配置的持久化、agent → role → session 的配置继承与合成属调用方（agent 中为 ConfigManager）；组件的配置类型只定义结构、默认值与「provider 默认 ← model 覆盖」这一级合成。
- **不含工具宿主与协议转换**：工具执行（Station）、工具定义与 MCP 的互转留在调用方，组件不依赖 MCP。

## 核心功能

### Epic 1：模型调用
- **目标**：按 provider 配置选择协议实现，构造请求、调用服务商 API、归一化响应，并支持失败重试与模型列表查询
- **依赖**：无（直接对接服务商 HTTP API）
- **用户故事**：
  - 作为一个调用方，我要用给定的 provider 配置完成一次对话补全，以得到模型回复
  - 作为一个调用方，我要区分「永久性配置错误」与「可重试的调用失败」，以避免无意义重试
  - 作为一个调用方，我要查询 provider 的可用模型列表，以校验模型名

### Epic 2：会话上下文
- **目标**：按会话标识维护独立的 LLM 上下文，支持恢复、增量追加、系统消息替换与超长归档
- **依赖**：无
- **用户故事**：
  - 作为一个调用方，我要按会话标识创建上下文并在重启后恢复，以保持对话连续性
  - 作为一个调用方，我要在上下文被压缩或重建前归档旧内容，以便回溯与审计
  - 作为一个调用方，我要在系统消息变化时自动应用并归档旧上下文，以切换提示词而不残留旧设定

### Epic 3：配置与数据结构
- **目标**：定义 provider/model 配置、LLM 请求参数与消息/响应结构，供调用方存储与传递
- **依赖**：kissbot-api（配置继承 merge 约定）
- **用户故事**：
  - 作为一个调用方，我要按 provider + model 合成有效参数（超时、重试、token 上限），以控制调用行为
  - 作为一个调用方，我要复用统一的 LLM 配置结构，以承载 agent / role / session 各级覆盖

## 模块划分

- **types**：上下文消息与模型响应结构（含工具调用数据与 LLM 侧工具定义）
- **config**：provider 配置（连接信息 + 默认模型参数 + 单模型覆盖）与 LLM 配置（可继承形态 + 有效形态），含配置继承 merge 实现
- **provider**：协议实现抽象与两个实现（OpenAI 兼容 / Anthropic）的构造入口、带重试的调用入口
- **session**：单会话上下文（内存消息 + 本地缓存 + 历史归档一体）
- **error**：组件错误与结果别名

配置继承的通用约定（`MergeBy` / `MergeSelf` / `MergeEffectiveConfig` 与字段表宏）由 kissbot-api 提供，本组件与 agent 共用。

## 功能流程

### 模型调用流程
```
调用方按 provider_type 选择实现：
  ├─ 未知类型 → 直接返回「不支持」（不触网）
  └─ openai / anthropic → 用 provider 配置构造实现
构造请求（模型、消息、工具定义、生成参数）
  → 调用 API（按有效模型配置的超时）
  ├─ 成功 → 归一化响应（正文、思考、工具调用、token 占用）
  ├─ 永久性错误 → 立即返回
  └─ 其它失败 → 按重试次数指数退避重试，用尽后返回最后一次错误
```

### 会话上下文流程
```
创建会话 → 从本地缓存恢复（正序全量回读 + 崩溃一致性清理）
追加消息 → 内存与缓存同时写入（新文件先落系统消息行）
设置系统消息 → 只存待定；下次构建上下文前对比应用
  ├─ 与当前一致 → 仅清空待定
  └─ 不一致 → 归档旧上下文 → 清空缓存 → 以新系统消息重建
重建/压缩 → 归档当前上下文（含系统消息）→ 清空缓存 → 写入新消息
```

## 关键设计

### 配置与执行分离
组件不读取任何全局配置：provider 的有效参数由调用方解析后传入，`provider_type` 分派也由调用方完成。这样同一个组件实例可以被多个模块使用而互不影响，也让「配置从哪来」（agent 的 nexus.json、其他模块自己的配置）不进入组件。

### 实例复用交给调用方
构造入口每次按配置返回新的实现实例（内含独立的 HTTP 客户端），组件自身不维护「provider 名 → 实例」的缓存，也不共享客户端。需要复用的调用方自行持有实例或按名缓存（agent 的 ProviderManager 即用工厂缓存做同名去重）；组件因此没有隐藏的进程级状态。

### 会话标识由调用方编码
组件只认一个不透明的会话标识字符串（用作缓存与归档的文件名段），标识如何编码、如何与业务会话（如 agent 的 agent+role+mode 三元组）对应，由调用方决定。组件因此不依赖任何业务身份概念。

### 错误分层
组件错误只覆盖模型调用与会话持久化。调用方在自己的错误类型上做逐变体映射，保持各自的错误表面与匹配逻辑不变；组件不感知调用方的业务错误（记忆、通道、命令等）。

### 复用方式
需要 LLM 的模块按同一套方式接入：定义自己的 provider 配置（或直接引用调用方已合成的有效配置）→ 构造 provider → 调用；会话上下文按自己的命名空间创建。摘要记忆与笔记工具因此无需依赖 agent，也无需重复实现 LLM 调用与上下文持久化。

## 与 agent 的关系

agent 是本组件的首个使用方：

- **provider**：agent 保留自己的 ProviderManager，承担「工厂去重 + provider_type 分派 + 有效模型配置解析」，实现与重试来自本组件（`create_*_provider` / `call_with_retry`）。
- **session**：会话上下文本体改用本组件的 Session/SessionContext；SessionManager 仍在 agent，负责按会话三元组去重与清理，并把三元组编码为 session_id。
