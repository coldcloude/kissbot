# kissbot-llm 组件设计

## 概述

LLM 基础库把「与模型服务商通信」和「会话上下文管理」从使用方中抽出，以程序库形式供需要模型的模块复用（当前使用方为 Agent 与摘要记忆服务）。它只承担两件事：按调用方给出的 provider 配置完成一次模型调用，并按调用方给出的会话标识管理一段上下文。

组件不持有配置、不做配置落盘与继承链合成、不管理会话集合，也不感知工具宿主与业务身份概念。这些职责留在调用方：配置的存储与分级由调用方的配置管理承担，会话的创建、持有与标识编码由调用方的执行流程承担。

## 核心功能

### Epic 1：模型调用

- **目标**：按 provider 配置构造请求、调用服务商、归一化响应，支持失败重试与模型列表查询
- **依赖**：无（直接对接服务商的 HTTP 接口）
- **用户故事**：
  - 作为一个调用方，我要用给定的 provider 配置完成一次对话请求，以得到模型回复
  - 作为一个调用方，我要区分永久性配置错误与可重试的调用失败，以避免无意义的重试
  - 作为一个调用方，我要查询 provider 的可用模型列表，以校验模型名并在管理界面上提供候选
  - 作为一个调用方，我要在一次调用中携带工具定义，以获得模型发起的工具调用

### Epic 2：会话上下文

- **目标**：按会话标识维护独立的上下文，支持从本地保存的上下文恢复、增量追加、系统提示词替换，以及上下文的归档与版本互换
- **依赖**：无
- **用户故事**：
  - 作为一个调用方，我要按会话标识创建上下文并在重启后恢复，以保持对话连续性
  - 作为一个调用方，我要在上下文被压缩或重建前把旧内容归档成版本，以便回溯
  - 作为一个调用方，我要在需要时把某个历史版本重新换回当前上下文，以复用以前的会话
  - 作为一个调用方，我要在系统提示词变化时让它自动生效，以切换设定而不残留旧内容

### Epic 3：配置与数据结构

- **目标**：定义 provider 与模型的配置结构、模型请求参数，以及上下文消息、工具调用与模型响应的结构
- **依赖**：kissbot-api（配置合并与字段访问的通用约定）
- **用户故事**：
  - 作为一个调用方，我要按 provider 默认值与单模型覆盖合成有效参数，以控制单次请求的超时与重试
  - 作为一个调用方，我要用同一套可继承的配置结构承载多级覆盖，以复用配置类型
  - 作为一个调用方，我要直接使用组件定义的消息与响应结构，以避免自建一套模型对话表示

## 模块划分

- **配置**：provider 连接信息与模型参数、可继承的模型请求参数及其有效形态，以及参数合成规则
- **协议实现**：协议实现的抽象与两个实现（OpenAI 兼容、Anthropic），负责请求构造、发送、响应解析与模型列表
- **调用入口**：带超时与重试的调用封装；按配置构造协议实现的入口
- **会话**：单个会话的上下文（内存消息、系统提示词、本地保存的上下文与版本）
- **数据类型**：上下文消息、工具定义、工具调用与归一化后的模型响应
- **错误**：组件自身的错误类型

## 功能流程

### 模型调用流程

```
调用方按 provider 类型选择协议实现（未知类型直接返回不支持，不发起请求）
  → 用 provider 配置构造实现
  → 构造一次请求（模型、消息、工具定义、生成参数）
  → 发送请求（超时按有效模型参数）
      ├─ 成功：解析响应并归一化（正文、思考、工具调用、结束原因、token 占用）→ 返回
      ├─ 永久性配置错误：立即返回
      └─ 其它失败：按重试次数指数退避后重试，用尽后返回最后一次错误
  → 模型列表查询：按 provider 的模型列表接口请求（固定超时、不重试）
```

### 会话上下文流程

```
创建会话（目录 + 会话标识）
  → 分别读取系统提示词与消息的本地文件，消息正序全量回读，无法解析的行跳过
  → 追加消息：内存与消息文件同时写入
  → 设置系统提示词：只记为待定（不写文件、不失败）
  → 构建上下文（只读）：当前系统提示词 + 内存消息，不应用待定值
  → 发送前构建完整上下文：比对待定值，不一致才重写系统提示词文件（不归档、不动消息）
  → 归档：为当前上下文生成版本并清空本地文件与内存（归档与清空成对执行）
  → 互换版本：先把当前上下文存成新版本，再把目标版本移入当前上下文并重新读取
```

## 关键设计

### 配置由调用方提供

组件不读取任何全局配置，也不决定 provider 类型如何分派：协议实现由调用方按类型构造，有效模型参数由调用方解析后传入。因此同一个组件可以被多个模块使用而互不影响，配置从哪来（agent 的配置、摘要记忆自己的配置）不进入组件。

### 实例复用交给调用方

构造入口每次返回新的协议实现实例，组件自身不维护 provider 实例的复用，也不共享连接。需要复用的调用方自行持有实例或按名复用，从而避免组件内出现隐藏的进程级状态。

### 会话标识不透明

会话标识对组件而言只是一个文件名安全的字符串，组件不解释其含义。标识如何编码、如何与业务对象对应，由调用方决定；组件因此不依赖任何业务身份概念，可以被不同调用方以各自的命名空间使用。

### 系统提示词延迟应用

设置系统提示词只记录待定值，真正生效发生在构建完整上下文时；比对后发现变化才重写文件，并且不产生版本、不改动消息文件。这样同一会话在多轮之间的系统提示词变更不会碎片化地产生版本，也不会让消息文件与提示词文件互相牵连。

### 归档即快照

归档把当前上下文文件直接移动为版本文件，不在归档时重新写入内容，因此版本内容与归档时刻的磁盘一致；互换版本同样是移动而非复制，目标版本被消耗。版本是只读快照，后续对话只发生在当前上下文。

### 一致性边界

上下文恢复依赖行级容错：单行解析失败跳过、文件缺失视为空，因此截断或局部损坏的文件仍能被读出一部分。组件不做落盘同步，也不对同一会话标识做跨进程协调，一致性的前提是同一会话在同一时刻只被一个进程使用；写入后未同步到磁盘的部分在断电时可能丢失。

### 两种协议的能力差异

两种协议的适配能力当前不对等：Anthropic 分支不发送工具定义、不解析工具调用，也不提供 token 占用，因此使用该协议时工具调用与上下文超长压缩不会发生；其单次输出上限未配置时使用内部固定值。调用方按协议能力选择使用方式。

### 错误分层

组件错误只覆盖模型调用与会话持久化，不含调用方的业务错误。调用方在自己的错误类型上做映射，从而保持各自对外的错误表面稳定。
