# kissbot-mcp 组件设计

## 概述

MCP 基础库按 MCP 规范实现一套极简的服务端与客户端能力，不依赖官方 SDK。它只实现服务发现、工具列表、工具调用三项方法与单端点的请求-响应传输，并在协议之上提供 kissbot 的工具分组与级联扩展。库内同时给出服务端与客户端的通用实现，使用方只需实现业务处理器即可对外提供工具能力，或作为客户端调用其他服务端。

## 核心功能

### Epic 1：协议消息与服务端分发

- **目标**：解析与构造协议消息，把请求分发到业务处理器，并校验请求携带的协议元信息与协议版本
- **依赖**：无（遵循 MCP 协议规范）
- **用户故事**：
  - 作为一个外部系统（MCP 客户端），我要向服务端发送请求，以查询服务信息或调用工具
  - 作为一个外部系统（MCP 服务端实现方），我要把业务处理逻辑接入通用服务端，以对外提供 MCP 服务而不处理协议细节
  - 作为一个外部系统（MCP 客户端），我要在请求不合法时得到明确的错误，以区分参数错误、版本不兼容与方法不存在

### Epic 2：服务发现与能力声明

- **目标**：向客户端报告服务端支持的协议版本、能力、身份与使用说明，并声明是否理解 kissbot 的级联扩展
- **依赖**：Epic 1（协议消息与服务端分发）
- **用户故事**：
  - 作为一个外部系统（MCP 客户端），我要查询服务端支持的协议版本与能力，以选择兼容的调用方式
  - 作为一个外部系统（MCP 客户端），我要读取服务端身份与使用说明，以在界面上展示并正确使用该服务端
  - 作为一个外部系统（MCP 客户端），我要判断对端是否理解级联祖先链，以决定是否可以把对端作为级联节点

### Epic 3：工具列表与分组归因

- **目标**：返回服务端可用的工具定义，并让每个工具都带有所属分组
- **依赖**：Epic 1（协议消息与服务端分发）
- **用户故事**：
  - 作为一个外部系统（MCP 客户端），我要查询工具定义，以把工具交给语言模型选择调用
  - 作为一个外部系统（MCP 客户端），我要读取每个工具携带的分组，以按分组圈定可用工具范围
  - 作为一个外部系统（第三方 MCP 服务端），我要在不声明任何 kissbot 能力的情况下被客户端接入，以复用现有实现

### Epic 4：工具调用

- **目标**：执行指定工具并返回结果，区分工具执行失败与协议级失败
- **依赖**：Epic 1（协议消息与服务端分发）
- **用户故事**：
  - 作为一个外部系统（MCP 客户端），我要调用服务端工具并取得结果，以让智能体完成外部操作
  - 作为一个外部系统（MCP 客户端），我要区分工具执行失败与调用本身不成立，以决定把结果回填上下文还是按通信失败处理
  - 作为一个外部系统（MCP 服务端实现方），我要返回结构化内容与多种内容块，以让工具结果保留原始形态

### Epic 5：单端点传输与客户端

- **目标**：以单端点请求-响应方式承载协议消息，提供服务端接线与客户端调用
- **依赖**：Epic 1（协议消息与服务端分发）
- **用户故事**：
  - 作为一个外部系统（kissbot 组件），我要以统一端点对外提供 MCP 服务，以被其他进程作为服务端调用
  - 作为一个外部系统（kissbot 组件），我要调用远端 MCP 服务端，以使用其工具能力
  - 作为一个管理员，我要限制 MCP 端点的访问来源，以降低本地服务被恶意网页访问的风险

## 模块划分

- **协议**：协议消息与错误码、请求与响应元信息、服务发现结构、工具定义与工具结果结构
- **服务端**：业务处理器抽象与请求分发（方法路由、协议版本校验、结果状态与身份的统一填充）
- **传输**：单端点请求-响应，负责请求校验、状态码映射与来源校验；以路由形式提供，认证由使用方叠加
- **客户端**：构造请求、发送、解析响应与错误归类

## 功能流程

### 服务发现流程

```
客户端发起发现请求（携带协议元信息）
  → 服务端校验元信息与协议版本
  → 业务处理器给出能力与使用说明
  → 服务端填充支持的协议版本与自身身份
  → 返回版本列表、能力、身份与使用说明
```

### 工具列表流程

```
客户端发起工具列表请求（携带协议元信息与祖先链）
  → 服务端校验元信息与协议版本
  → 业务处理器给出工具定义（每个工具携带自身分组）
  → 服务端填充结果状态与自身身份
  → 返回带分组归因的工具定义
```

### 工具调用流程

```
客户端发起工具调用请求（工具名、参数、祖先链）
  → 服务端校验元信息、协议版本与调用目标
  → 业务处理器执行工具：
       ├─ 工具执行失败：结果标记为失败并携带错误信息（仍是正常响应）
       └─ 协议级失败（如级联自环）：返回协议错误响应
  → 返回工具结果或协议错误
```

### 传输校验流程

```
请求到达单端点
  → 校验请求来源（白名单或本机回环）
  → 解析请求体并取出请求标识
  → 校验请求头与请求体的方法、协议版本、调用目标一致
  → 校验请求元信息完整、协议版本受支持
  → 分发到对应方法
  → 按结果映射状态码：方法不存在映射为未找到，其余（含工具执行失败）为成功响应
```

## 关键设计

### 每个请求自带上下文

协议版本、客户端身份与能力随请求携带，服务端不依赖连接或会话状态即可独立处理每个请求；服务端在响应中回带自身身份，客户端无需先握手即可直接调用任意方法。因此传输层不需要会话管理，也没有流式响应与长连接通知。

### 工具级失败与协议级失败分层

工具自身的执行失败作为工具结果的一部分返回（标记失败并携带错误信息），协议或请求本身的问题作为协议错误返回。调用方据此区分「工具没执行成功」与「调用不成立」，前者可以作为工具结果回填模型上下文，后者按通信失败处理。

### 内容块由生产方决定

工具结果的内容块由工具实现决定，服务端与传输层原样回传，不解释块类型、不把结构化数据合成文本、不改写数组。结构化结果的机器可读形态与它在内容块中的镜像表示也都由生产方给出。

### 分组是扩展而非协议

分组是 kissbot 在协议之上的扩展，随工具定义的元信息携带，不改变方法参数的形状；服务端不在工具列表上做过滤，按分组圈定范围由调用方在拿到工具定义后自行完成。分组归因不需要对端声明：携带分组即归因于该分组，未携带则归因于调用方约定的默认分组，因此标准 MCP 服务端无需改造即可接入。

### 级联与防环

级联请求携带祖先链（根到当前父节点的站点标识列表），任一层发现自己的站点标识已在链中即拒绝，避免级联成环。是否为链上节点提供扩展能力属于可选能力，服务端在服务发现中声明；不理解该扩展的对端只会看到一个被忽略的未知元信息键。

### 扩展键与规范键分列

协议规定的元信息键保持规范名称，kissbot 自身扩展使用自有前缀，以保证与标准客户端、服务端的互操作性，也便于规范升级时区分归属。

### 最小能力面

只实现服务发现、工具列表、工具调用与单端点请求-响应传输，不实现流式响应、协议级会话与协议级通知。使用方需要流式或通知能力时另行扩展，而非在本库中堆叠能力。
