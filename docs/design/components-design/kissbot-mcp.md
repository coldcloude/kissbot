# kissbot-mcp 组件设计

## 概述

kissbot-mcp 是 kissbot 的 MCP 基础库，不依赖 MCP 官方 SDK，按 MCP 规范实现极简的 MCP 协议通信。它只保留服务发现、工具列表、工具调用三项能力，并在协议之上提供 kissbot 的工具分组扩展。库内同时提供服务端与客户端两侧的通用实现，供 kissbot 组件（如 Station）复用，使组件无需自行处理协议细节即可对外提供或调用 MCP 能力。

## 核心功能

### Epic 1：协议消息与服务端分发
- **目标**：解析与构造协议消息，把请求分发到业务处理器，并校验请求携带的协议元数据与协议版本
- **依赖**：无（遵循 MCP 协议规范）
- **用户故事**：
  - 作为一个外部系统（MCP 客户端），我要向 MCP 服务端发送请求，以查询服务信息或调用工具
  - 作为一个外部系统（MCP 服务端），我要按协议回应请求，以被 MCP 客户端集成
  - 作为一个外部系统（kissbot 组件），我要把业务处理逻辑接入通用服务端，以对外提供 MCP 服务

### Epic 2：服务发现
- **目标**：向客户端报告服务端支持的协议版本、能力与身份，并借此声明 kissbot 级联扩展能力
- **依赖**：Epic 1（协议消息与服务端分发）
- **用户故事**：
  - 作为一个外部系统（MCP 客户端），我要查询服务端支持的协议版本与能力，以选择兼容的协议版本并判断可用功能
  - 作为一个外部系统（MCP 客户端），我要读取服务端身份与使用说明，以在界面上展示并正确使用该服务端
  - 作为一个外部系统（MCP 客户端），我要一次性判定对端是否支持 kissbot 级联扩展，以判断对端是否理解级联祖先链

### Epic 3：工具列表与分组归因
- **目标**：返回服务端可用的工具定义，并让每个工具都带上所属分组
- **依赖**：Epic 1（协议消息与服务端分发）
- **用户故事**：
  - 作为一个外部系统（MCP 客户端），我要查询工具定义，以把工具交给语言模型选择调用
  - 作为一个外部系统（MCP 客户端），我要读取每个工具携带的分组，以按任务或场景圈定可用工具范围
  - 作为一个用户，我要为不同会话启用不同的工具分组，以控制智能体可用的工具范围

### Epic 4：工具调用
- **目标**：调用指定工具并返回执行结果，区分工具执行失败与协议错误
- **依赖**：Epic 1（协议消息与服务端分发）
- **用户故事**：
  - 作为一个外部系统（MCP 客户端），我要调用服务端工具并取得结果，以让智能体完成外部操作
  - 作为一个外部系统（MCP 客户端），我要区分工具执行失败与协议错误，以正确回填工具调用结果

### Epic 5：HTTP 传输与客户端
- **目标**：以单端点请求-响应方式承载协议消息，提供服务端接线与客户端调用
- **依赖**：Epic 1（协议消息与服务端分发）
- **用户故事**：
  - 作为一个外部系统（kissbot 组件），我要以统一端点对外提供 MCP 服务，以被其他进程作为 MCP 服务端调用
  - 作为一个外部系统（kissbot 组件），我要调用远端 MCP 服务端，以使用其工具能力
  - 作为一个管理员，我要限制 MCP 端点的访问来源，以降低本地服务被恶意网页访问的风险

## 模块划分

- **protocol**：协议消息类型与常量（JSON-RPC 消息、请求/响应元数据、服务发现与工具相关结构、错误码）
- **server**：业务处理器抽象与服务端分发（方法路由、结果类型与服务端身份填充、协议版本协商）
- **http**：单端点请求-响应传输（请求校验、状态码映射、访问来源校验）；以 Router 形式提供，认证由调用方叠加
- **client**：客户端（构造请求、发送、解析响应、错误归类）

## 功能流程

### 服务发现流程
```
客户端发起发现请求（携带协议元数据）
  → 服务端校验协议元数据与协议版本
  → 业务处理器给出能力与使用说明
  → 服务端填充支持的协议版本与服务端身份
  → 返回协议版本列表、能力、身份与使用说明
```

### 工具列表流程（含分组归因）
```
客户端发起工具列表请求（携带协议元数据）
  → 服务端校验协议元数据与协议版本
  → 业务处理器给出工具定义（每个工具携带自身分组）
  → 服务端填充结果类型与服务端身份
  → 返回带分组归因的工具定义
```

### 工具调用流程
```
客户端发起工具调用请求（工具名 + 参数）
  → 服务端校验协议元数据、协议版本与调用目标
  → 业务处理器执行工具：
       ├─ 工具执行失败 → 结果标记为失败，携带错误码与文案（仍为成功响应）
       └─ 协议级失败（如循环调用） → 返回协议错误响应
  → 返回工具结果或协议错误
```

### 请求校验流程
```
收到请求
  → 校验访问来源（浏览器来源白名单）
  → 解析请求体
  → 校验协议版本请求头与请求体一致、且在服务端支持的版本列表内
  → 校验方法请求头与请求体一致
  → 调用类请求校验目标名称请求头一致
  → 分发到业务处理器 → 按结果映射响应状态码
```

## 关键设计

### 协议元数据随请求携带
请求自带协议版本、客户端身份与能力，服务端不依赖连接或会话状态即可独立处理每个请求。服务端在响应元数据中回带自身身份，客户端无需先做握手即可直接调用任意方法。

### 工具级失败与协议级失败分层
工具自身的执行失败作为工具结果的一部分返回（结果标记失败并携带错误码与文案），协议或请求层面的问题作为协议错误返回。调用方据此区分「工具执行不成功」与「调用本身不成立」，前者可作为工具结果回填上下文，后者由调用方按通信失败处理。

### 内容块由生产方决定，服务原样回传
工具结果的内容块由工具（结果生产方）决定，服务端与传输层只把内容块数组原样回传，不解释块类型、不把结构化数据合成文本、不改写数组。结构化结果的机器可读形态与它在内容块中的镜像表示也都由生产方给出，协议库不替生产方做这类渲染决策。

### kissbot 分组扩展
分组是 kissbot 在 MCP 协议之上的扩展，用于按任务或场景圈定可用工具范围。分组是工具的固有属性，随工具定义的工具元数据（规范 `Tool._meta`）携带，不改变方法自身的参数形状；服务端不在工具列表上做分组过滤，按分组圈定范围由调用方（kissbot 中为会话配置）在拿到工具定义后自行完成。

### 扩展能力经服务发现声明
级联扩展属于可选能力，服务端在服务发现的能力集合中声明是否理解级联祖先链，客户端据此判断对端是否理解该扩展键。分组归因不需要声明：工具定义携带 `kissbot/group` 即归因于该分组，未携带则归因于调用方约定的默认分组，因此标准 MCP 服务端无需任何改造即可接入。

### 规范保留键与扩展键分列
协议规定的元数据键保持规范名称不变，kissbot 自身扩展使用自有前缀（键名见 [kissbot-mcp 技术规格](../../spec/kissbot-mcp.md)），以保证与标准 MCP 客户端、服务端的互操作性。

### 最小能力面
只实现服务发现、工具列表、工具调用三项方法与单端点请求-响应传输，不实现流式响应、协议级会话与长连接通知；调用方需要流式或通知能力时另行扩展。
