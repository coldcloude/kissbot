# kissbot-memory-ego 组件设计

## 概述

自我认知服务管理 agent 的自我认知设定，作为独立服务运行。自我认知分为两部分：**客观设定**描述 agent 自身与它所认知的外部个体；**角色设定**描述 agent 在特定角色下的定位与关系。Agent 在建立会话时读取这些数据并拼装为系统提示词，从而知道自己是谁、面对谁、扮演什么角色。

服务同时提供搜索与名称补全能力，供管理界面查询与选择。

## 核心功能

### Epic 1：agent 元数据管理

- **目标**：管理每个 agent 的身份标识与描述，支持创建、查询、列举、修改描述与复制
- **依赖**：kissbot-memory（目录与存在标记）
- **用户故事**：
  - 作为一个管理员，我要为 agent 指定一个易读的标识并创建它，以在系统中登记这个 agent
  - 作为一个管理员，我要查询某个 agent 的元数据，以确认它的身份与描述
  - 作为一个管理员，我要列出所有已创建的 agent，以了解系统中有哪些 agent
  - 作为一个管理员，我要修改 agent 的描述，以更新它的自我认知
  - 作为一个管理员，我要基于已有 agent 复制出一份元数据，以快速创建设定相近的 agent

### Epic 2：个体识别信息管理

- **目标**：管理 agent 认知的外部个体，包括个体名称、在各通道上的身份、与本 agent 及其他个体的关系
- **依赖**：Epic 1（agent 元数据管理）
- **用户故事**：
  - 作为一个管理员，我要为 agent 添加一个外部个体，以让它能识别对话方
  - 作为一个管理员，我要给一个个体关联多个通道身份，以把同一个人在不同通道上的账号归并为一个个体
  - 作为一个管理员，我要维护个体与本 agent、与其他个体之间的关系，以使 agent 理解人物关系
  - 作为一个管理员，我要重命名个体或批量替换个体列表，以调整 agent 的认知

### Epic 3：角色设定与角色关系管理

- **目标**：管理 agent 可扮演的多个角色，以及角色与其他角色、其他角色所关联个体之间的关系
- **依赖**：Epic 1、Epic 2
- **用户故事**：
  - 作为一个管理员，我要为 agent 创建一个角色，以指定它的名称、展示名与描述
  - 作为一个管理员，我要列出某个 agent 的全部角色，以了解它可以扮演什么
  - 作为一个管理员，我要修改角色的描述或展示名，以调整角色的行为设定
  - 作为一个管理员，我要为角色建立与其他角色的关系，以描述同一场景下各方的关系
  - 作为一个管理员，我要从已有角色复制一份设定，以快速创建相近的角色

### Epic 4：搜索与名称补全

- **目标**：对 agent 与角色提供按名称、描述的子串搜索与按名称前缀的补全
- **依赖**：Epic 1、Epic 3
- **用户故事**：
  - 作为一个管理员，我要按名称或描述搜索 agent，以找到目标 agent
  - 作为一个管理员，我要按名称、展示名或描述搜索角色，以找到目标角色
  - 作为一个管理员，我要输入名称前缀获得补全建议，以快速定位
  - 作为一个管理员，我要在修改设定后立即得到准确的搜索结果，以在不重启服务的情况下看到效果

### Epic 5：向 agent 提供自我认知读取

- **目标**：为 agent 提供读取客观设定与角色设定的接口，供其构建系统提示词
- **依赖**：Epic 1~3
- **用户故事**：
  - 作为一个外部系统（agent），我要读取 agent 元数据、个体识别与角色设定，以拼装系统提示词
  - 作为一个外部系统（agent），我要在某个角色尚未配置时得到「不存在」的明确结果，以回退到默认提示词
  - 作为一个外部系统（agent），我要在服务未配置或请求失败时得到错误，以决定是否降级

## 模块划分

- **agent 元数据管理**：元数据文件的读写、创建与复制、描述更新
- **个体识别管理**：个体条目的增删改、通道身份集合与两类关系表的替换
- **角色设定管理**：角色本体与角色关系表的读写、创建与复制
- **搜索索引**：全文子串索引与名称前缀补全索引，按需同步
- **存储与读取**：按 agent 与角色的分层读取、写入与文件组织
- **API 服务**：对外的读写与搜索接口、认证与统一响应

## 功能流程

### 写入流程

```
管理员提交写请求
  → 校验标识（agent、角色、个体等代号只允许字母、数字与下划线）
  → 读取该 agent（或该 agent 的角色）的现有数据
  → 在副本上修改
  → 写回对应的数据文件
  → 使后续读取看到新内容
  → 标记受影响的条目需要更新搜索索引
```

### 读取流程

```
收到读请求
  → 读取该 agent（或该角色）的数据并返回
  → 读取不触发索引同步
```

### 搜索流程

```
收到搜索或补全请求
  → 先更新搜索索引中待更新的条目（内容未变则跳过、名称变化时重建补全项）
  → 在子串索引或前缀补全索引中检索
  → 返回匹配的标识列表（角色搜索可按 agent 过滤）
```

### 服务启动流程

```
读取配置（监听地址与端口）
  → 扫描记忆根目录下带存在标记的 agent
  → 加载各 agent 的元数据与角色设定，建立搜索索引
  → 开始提供服务
```

## 关键设计

### 客观设定与角色设定分离

客观设定描述「agent 是谁、认识谁」，角色设定描述「此刻扮演谁、与其他角色是什么关系」。二者分别存储、分别读取，agent 在建立会话时按需要组合。这样同一个 agent 可以在不同角色之间切换，而客观设定保持一致。

### 标识即目录与键

agent 标识同时是目录名，角色标识与个体名称同时是文件内与关系表中的键。因此标识必须满足文件名安全与可比较的要求：只允许字母、数字与下划线。标识在创建后不可修改；需要改名时创建新条目并复制内容。

### 引用而非嵌套

个体之间、角色之间、角色与个体之间都通过标识互相引用，而非把对方的内容嵌入自身。这样修改一个个体不会波及引用它的所有角色，也避免同一份数据出现多个副本。

### 读取与写入

读取按 agent 与角色分层进行；写入以整份设定为单位提交，提交后对后续查询可见。读取多于写入，因此每次写入承担整份文件的写回代价，而读取不必等待写入完成。

### 搜索索引按需同步

写操作只标记需要更新，读操作在检索前才更新索引，更新时按内容差异做增量处理。启动时加载全部已创建的 agent 与角色建立索引，保证服务刚启动就能搜索。这使写入路径不必等待索引重建，搜索又能反映最新数据。

### 索引只在进程内

搜索索引不持久化，也不监听磁盘变化；多个实例或手工修改文件不会被索引感知。索引的准确性以「通过本服务写入」为前提。

### 无变化则不通知外部

自我认知的修改不会主动通知 agent；agent 在下一次建立会话时读取到新内容。这样 agent 不必处理设定变更事件，代价是已建立的会话继续使用旧设定。
