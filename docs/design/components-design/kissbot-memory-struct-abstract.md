# kissbot-memory-struct-abstract 组件设计

## 概述

摘要记忆实现组件，是记忆结构框架（kissbot-memory-struct）的一个实现模块，作为独立服务运行。组件用大模型把原始记忆划分为 **case（专案）**：一个 case 的记忆单独摘抄一份完整记录并生成摘要；新记忆数据经判定归档到 case，必要时自顶向下分层归并；新消息到达时先定位所属 case，取 case 的摘要或原文作为上下文。

这里的 case 是本组件对记忆切分与归并的产物，与 agent 侧 role-event 的 **event（事件）** 区分：角色模式与事件模式两种记忆后缀共用同一个角色的 case 树，事件模式固定对应一个顶层叶子 case。

组件只负责「记忆的 case 化组织与定位」，不改变原始记忆的存储，也不消费定位结果——定位结果如何进入 nexus 的上下文由后续独立实现（输入处理器或原生工具）承担。

## 核心功能

### Epic 1：新数据订阅与懒处理
- **目标**：订阅记忆存储的新数据通知并在「记忆后缀 + 通道」（通道 = messenger + agent 在该通道绑定的用户 + 群组）粒度登记变化；归档计算推迟到查询时统一进行
- **依赖**：kissbot-memory-store（新数据通知服务）、kissbot-memory（原始记录的读取与索引）
- **用户故事**：
  - 作为一个外部系统（记忆存储模块），我要在写入新记录后向已连接的摘要记忆广播通知，以使摘要记忆知道有新数据
  - 作为一个外部系统（记忆存储模块），我要在通道消息的通知中给出 agent、记忆后缀与通道，以使摘要记忆能精确登记是哪个后缀哪个通道发生了变化
  - 作为一个调用方，我要一个显式的手动触发归档入口（以及在定位时顺带处理本通道待归档记录），以在需要时让结果反映最新记忆，而不依赖隐藏的时机规则
  - 作为一个管理员，我要一个通道的记录只进它自己通道的批次，以使多个通道（不同 messenger / 用户 / 群组）的记忆互不吞并

### Epic 2：case 分组、归档与分层归并
- **目标**：把某通道的待处理记录交大模型按 case 分组，属于当前 case 的组直接并入、其余组各自归并到已有 case 或新建 case 节点
- **依赖**：Epic 1（待处理批次）、kissbot-llm（模型调用）
- **用户故事**：
  - 作为一个管理员，我要新记忆数据自动分组并归档到合适的 case，以使记忆按 case 组织而无需人工整理
  - 作为一个管理员，我要属于当前 case 的组直接并入当前 case、其他组自顶向下归并到已有 case 之下，以使 case 形成多层结构
  - 作为一个管理员，我要角色模式的逐层判定只看角色子树的 case，以使事件模式的固定 case 不被并入角色 case
  - 作为一个调用方，我要事件模式下的记忆整体归为一个顶层叶子 case，以使按事件隔离的上下文不被再次切分

### Epic 3：case 内容与摘要维护
- **目标**：为每个 case 保存归属它的原始记录副本与大模型摘要，内容变化后重算摘要并级联更新祖先摘要
- **依赖**：Epic 2（case 与层级）、kissbot-llm（模型调用）
- **用户故事**：
  - 作为一个调用方，我要 case 自包含原文副本与摘要，以使 case 不受原始记录流后续变化的影响
  - 作为一个调用方，我要父 case 摘要涵盖其子 case 内容，以使大 case 摘要完整反映其内容

### Epic 4：case 定位与上下文供给
- **目标**：给一批消息（可跨通道）定位其涉及的全部 case 并给出 case 标识；摘要与原文副本由调用方按需取
- **依赖**：Epic 2、Epic 3（case 内容与层级）、kissbot-llm（模型调用）
- **用户故事**：
  - 作为一个调用方，我要一次传入多条消息并取回它们涉及的全部 case 标识与分组，以决定用哪些 case 的记忆
  - 作为一个调用方，我要定位对每条消息都按它所在通道的当前 case 比对，以使多通道消息各自命中自己的话题
  - 作为一个调用方，我要定位时新消息与已存记录去重、一并分析，以使同一条消息不被分析两次、case 归属与归档结果一致
  - 作为一个调用方，我要按 case 标识分别取摘要、全部原文、指定位置之后的原文、结尾若干条原文，以按需拼装上下文而不必一次拉全量
  - 作为一个调用方，我要新话题也有 case 标识（本次建出、记忆条数为 0），以使同一话题后续写入记忆时并入同一 case

### Epic 5：case 查询与管理
- **目标**：提供 case 树、case 摘要与原文副本（全部 / 指定之后 / 结尾若干条）的查询，以及手动触发与重建能力
- **依赖**：Epic 2、Epic 3
- **用户故事**：
  - 作为一个管理员，我要查询某角色的 case 树与该记忆后缀的 case 摘要，以核对记忆组织是否正确（各通道水位与当前 case 指针见数据目录下的状态文件）
  - 作为一个调用方，我要按位置增量续读 case 的原文副本，以在不重复拉取的前提下跟进 case 内容
  - 作为一个调用方，我要只取 case 结尾若干条原文副本，以用最近若干条拼装上下文
  - 作为一个管理员，我要手动触发或重建某记忆后缀的归档，以处理通知缺失或导入历史记录
  - 作为一个外部系统（记忆管理界面），我要读取 case、摘要与原文，以在界面上展示与维护

## 模块划分

- **通知订阅**：连接记忆存储的通知服务，维护长连接与重连
- **归档调度**：登记「记忆后缀 + 通道」的待处理标记；只有定位（带本批消息）、手动触发与重建会提取各通道水位之后的记录，与（定位请求的）本批消息统一按通道分组，逐通道交给归档器处理
- **记录读取**：从共享记忆文件读取四类原始记录，并标注每条记录的通道归属（通道记录按自身身份，思考/工具记录按 key 关联的占位通道记录）
- **case 树管理**：case 节点、层级与各记忆后缀各通道当前 case 指针的读写和持久化
- **归档器**：按通道把「水位之后的记录 + 可选的只用于定位的新消息」去重合并后分块处理——先只读定位（逐组判定落点），再只对有记录的组落地（新建 case、追加记录、摘要级联、逐块落盘）
- **分组与落位**：第 1 轮按 case 分组（并标记当前 case 组），当前 case 组直接并入，其余组逐层判定落点（归入已有 case / 需要新建）；判定不改树，是否落地由组里有没有记录决定
- **摘要器**：case 摘要生成与祖先摘要级联重算
- **逐层判定与结果汇总**：分组后逐组判定落点（判定只读、不改树；是否落地由组里有没有记录决定），并把分组汇总成「消息涉及的全部 case + 分组」
- **API 服务**：对外查询、定位与管理接口（case 树/case 摘要/原文副本查询与分页/定位/手动触发/重建）
- **配置**：组件配置读取（模型 provider、分块上限、服务地址）
- **模型接入**：复用 LLM 基础库完成模型调用与会话上下文管理

## 功能流程

### Epic 1 懒处理流程
记忆存储写入新记录 → 广播通知 → 摘要记忆**只登记待处理标记**（通道消息按「记忆后缀 + 通道」登记；思考/工具通知、后缀未知通道、首次加载、通知重连按该后缀全部通道登记），不读盘、不调模型。
处理入口只有两种：`locate`（带本批消息）、`/abstract/rebuild` 的 rebuild=false（手动触发）与 rebuild=true（重建）→ 读一次共享记忆文件，把**每个通道**水位之后的记录各自成批（通道记录按自身身份，思考/工具记录按 key 找同 key 的占位通道记录）→ 逐批归档 → 逐块落盘。case 树/摘要/原文查询只读，不触发归档。
没有待处理标记时查询不做任何额外工作；处理失败时标记保留，下次查询重试。

### Epic 2 case 归档流程
按通道取待归档批次 → 事件模式的记忆后缀：直接并入该后缀固定的顶层叶子 case `event-{事件标识}`（不分组、不做定位判定）。
角色模式的记忆后缀（同一角色的 case 树）：
1. 第 1 轮（分组轮）——把该通道当前 case 与全部待处理消息一起交给模型，模型按 case 分组并标记哪些组属于当前 case；标记为当前 case 的组直接并入当前 case，其余组以组为单位进入第 2 轮。
2. 第 2 轮起逐层判定——每个组自顶层起逐层给出当层全部**角色 case** 摘要，产生两种结果之一：并入某 case（该 case 为叶子时内容并入，非叶子时下潜到其子层继续判定）；新建叶子 case（当层未命中时在该层新建；只含新消息的组也建，记忆条数为 0）。事件模式的固定 case 不在候选里，两种模式互不并入。
3. 落地后按 case 聚合追加原文副本 → 重算受影响 case 摘要 → 级联重算祖先摘要 → 该通道当前 case 指针指向本批最后一个组落入的 case。
case 树按**角色**共享一棵，同一角色的角色模式与事件模式都归并到同一棵树里；当前 case 指针按「记忆后缀 + 通道」各记一份。

### Epic 3 摘要生成流程
case 内容变化 → 汇总该 case 的直接记录与子 case 摘要 → 模型生成摘要 → 更新节点 → 自底向上重算受影响的祖先摘要。

### Epic 4 case 定位流程
一批消息到达 → ① 提取：读一次该记忆后缀的共享记忆取出各通道水位之后的待归档记录（pending），与本批消息一起**按通道分组**（pending 与本批消息都可为空）→ ② 定位（只读）：对每个通道调用归档入口 `archive(记录, 消息)`，在单通道批次内按 `msg_id` 去重（`msg_id` 为空的不参与去重、原样保留），把「记录 + 不重复的新消息」合并成一个批次；角色模式用「该通道当前 case + 合并批次」做第 1 轮分组，再逐组判定落点——标记为当前 case 的组命中该通道当前 case，其余组自顶层逐层判定（命中叶子即该组 case；命中非叶子后其子层都未命中则命中该父 case；顶层未命中则该组是新话题）→ ③ 落地 + 存储 + 返回：逐组建出/命中 case（新话题一律建出叶子 case，只含新消息的组记忆条数为 0），有记录的组再追加原文副本、重算摘要、推进水位并更新当前指针；最后把消息分组映射回请求下标合并成「消息涉及的全部 case（去重）+ 分组」。
事件模式不分组、不做定位判定：整个后缀固定归入 `event-{事件标识}` 顶层叶子 case（不存在则建出，记忆条数为 0）。
**pending 是否为空走同一套判定**：判定结果只有「归入某已有 case」和「需要新建在某父 case 之下」两种，两者都落地；差别只是有记录的组还要写原文副本、重算摘要、推进水位。
只要调用 locate，输入就是「pending + 消息」，没有「先归档再定位」的两段式，也没有第二轮补齐循环；`messages` 为空时（手动触发 / 重建）即原来的归档，只有记录落盘、不返回消息结果。
角色树里还没有角色 case 时没有 case 可比对（不做逐层判定），第 1 轮分组后每个组建出记忆条数为 0 的 case；事件模式下 `event-{id}` 不存在时也建出。
上下文装配交给调用方：拿到标识后按需取摘要（`case/summary`）、全部原文（`case/records`）、指定位置之后的原文（`case/records-after`）或结尾若干条（`case/records-tail`）。

### Epic 5 查询与管理流程
查询请求 → 直接由 case 树管理按角色读取树、按记忆后缀读取各通道当前 case 指针（原文查询再读 case 原文副本）→ 返回；**查询只读，不触发归档**。需要处理待归档记录时由调用方显式调 `/abstract/rebuild` 的 rebuild=false（或走定位）。
手动触发 → 忽略待处理标记，强制把该后缀各通道水位之后的记录处理一次。
重建请求 → **只清空本次记忆后缀自己的 case**（角色模式清该角色的角色子树；事件模式只清本后缀固定的 `event-{事件id}`，同一角色的其他事件后缀不受影响）+ 该后缀的指针/水位，再按共享记忆文件重新构建（各通道分别处理）。

## 关键设计

### case 树组织
case 以 (agent, 角色) 为作用域组织成一棵树，跨年份持续累积；大 case 可以包含子 case。每个 case 保存归属它的原始记录副本与大模型摘要，内容自包含。父 case 摘要由自身直接记录与子 case 摘要合成。
**同一角色的角色模式与事件模式共用这一棵树**（同一句柄、同一目录），但各走各的子树：角色模式分配的 case id 为 `role-{N}`（`role-1`、`role-2`…，角色树内递增），事件模式固定为顶层叶子 `event-{事件标识}`；角色模式的逐层判定候选只有角色 case。
归档只新建叶子 case；父子层级由后续「建立 case 间关联关系」与「把多个 case 合并为大 case」的定时程序产生（预留），因此分层归并的下潜分支在当前阶段不会被触发。

### 两级作用域：角色决定树，记忆后缀决定输入与状态
- **角色（`AgentRole { agent_id, role }`）**决定 case 树：同一角色的角色模式与事件模式共用同一棵树、同一个 `ScopeManager` 句柄与同一个目录。
- **记忆后缀（`RoleEvent`，即外部传入的 `role`）**决定输入与状态：按**第一个** `-` 拆分，无 `-` 为角色模式、含 `-` 为事件模式（前半为角色名，后半为事件标识；角色名不允许含 `-`，事件标识可以含 `-`）。原始记录读取、水位、当前 case 指针、模型会话都按后缀区分。
- **模型会话作用域（`ModelScope { agent_id, role_event }`）**：模型会话上下文按它隔离，同一后缀的连续判定共享上下文。

### 按通道隔离的记忆流
case 树按角色组织（同一角色的记忆是一棵树），而「最近被并入内容的 case」（当前 case 指针）与「已处理水位」按「记忆后缀 + 通道」各记一份：通道 = `messenger_id + self_user_id + group_id`（agent 在该通道绑定的用户 + messenger + 群组），发送者 `user_id` 不参与——本人消息与对话对方的消息因此属于同一通道。
查询时按通道分别切出待处理记录、各自成批归档、各自推进水位，一个通道的归档不影响其他通道；定位时用新消息的通道取当前 case 指针。归档与定位都**按通道分开调用**，批次内只有该通道的记录与消息（这也是判重只看 `msg_id` 的前提）。这样同一角色同时服务多个通道时，各通道的归档互不吞并、上下文互不串味。

### 两种记忆来源
- **角色模式**（记忆后缀不含 `-`）：作用域内的记录经模型判定切分为 case，可多层归并。
- **事件模式**（记忆后缀为 `角色名-事件标识`）：整个后缀固定对应一个顶层叶子 case（`event-{事件标识}`），内部不再划分，也不参与分层归并。

### 当前 case 优先
每个「记忆后缀 + 通道」维护一个当前 case 指针，指向该通道最近被并入内容的 case。归档与定位都用同一套分组轮：把**该通道**的当前 case 与消息一起交给模型，由模型标记哪些消息属于当前 case——标记的组直接命中，其余才扩大到更大范围（逐层下探），以落实「优先选择当前 case」并控制调用开销。

### 归档以通道为准
批次按通道切分：通道记录按自身身份归属，思考与工具记录按自身的 key 找到同 key 的思考/工具占位通道记录后归属到对应通道，随该通道的批次一并归档，使 case 完整保留推理与行动轨迹；找不到占位记录的记录不属于任何通道，也不进入任何批次。

### 归档时机：通知只登记，定位、手动触发与重建才计算
通知只回答「哪个记忆后缀哪个通道有新数据」，不做任何计算；归档只在**显式入口**发生：定位（带本批消息，顺带处理该后缀各通道的 pending）、`/abstract/rebuild` 的 rebuild=false（手动触发）、rebuild=true（重建）。这样既不依赖任何隐藏的归档时机规则（无超时、无本人/非本人消息判定），查询也不必承担归档开销——case 树/摘要/原文查询是纯读。待处理标记只影响「有没有新数据要处理」，没有标记且没有消息时才不读盘、不调模型。

### 定位就是「pending + 消息」的一次归档：判定与落地分开
定位不再「先归档待处理记录、再单独定位消息」，也不是「有待处理标记才归档、否则走另一条只读路径」，而是**一条路径**：
1. **提取**：读一次共享记忆，取出该记忆后缀各通道水位之后的待归档记录（pending），与本批消息一起**按通道分组**（pending 与本批消息都可为空）。
2. **定位（只读）**：每个通道调用同一个归档入口 `archive(记录, 消息)`——按 `msg_id` 去重（消息标识来自 incoming_message / outgoing_message_response，思考/工具占位记录为空；为空的一律不参与去重、原样保留）合并成一个批次，角色模式做第 1 轮分组后**逐组判定落点**：`归入某已有 case` 或 `需要新建在某父 case 之下`；事件模式固定归入 `event-{事件标识}`。判定完全不改树，**pending 是否为空走的是同一套判定**，因此「有记录的组」和「只定位的组」不是两个分支。
3. **落地 + 存储 + 返回**：逐组建出/命中 case——新话题一律建出叶子 case（只有消息的组也建，记忆条数为 0，便于这些消息之后写入记忆时并入同一 case）；有记录的组再追加原文副本、重算摘要、推进水位、更新当前指针。最后把各通道的消息分组映射回请求下标合并。

没有两个驱动：只要调用 locate，输入就是「pending + 消息」。没有待处理标记且没有消息（纯查询且无变化）时才不读盘；带消息时总会读一次共享记忆提取 pending，因此漏掉通知也能在下一次定位时被顺带归档。

分块、逐块落盘与摘要级联都由归档器承担（记录按 `max_batch_records` 分块），因此同一条入口既能在带消息时返回定位结果，也能在没有消息时单独当作归档使用（手动触发 / 重建）。

### 分组由模型决定，批次边界不再由规则切分
第 1 轮把当前 case 与整批待处理消息一起交给模型，让模型按 case 分组并标记当前 case 组：属于当前 case 的组直接并入，其他组各自作为独立单元进入分层归并。批次边界由此由内容决定，而不是由「本人消息 / 超时」这类时间与身份规则切分。定位触发时批次是「待归档记录 + 去重后的新消息」的合并结果，对模型而言仍是同一个按时间排列的消息流。事件模式不分组。

### 分级候选控制上下文规模
第 1 轮只给**该通道的当前 case**摘要（外加待处理消息本身），第 2 轮起才逐层给出当层全部**角色 case** 摘要，避免一次把全部 case 摘要送入模型。
待处理消息按 `max_batch_records` 分块（定位触发时按合并后的批次分块），保证单次送入模型的消息量有界；逐层判定最多下潜 `max_case_depth` 层（默认 16）。

### 模型接入
模型调用与会话上下文复用 LLM 基础库，会话按模型会话作用域 `ModelScope { agent_id, role_event }` 隔离（同一角色下角色模式与事件模式各自一个会话）；组件自身持有 provider 配置，不读取 agent 的配置。

### 关联 case 与 case 合并（预留）
case 之间的关联关系、关系描述，以及关联 case 摘要纳入上下文，留待后续实现；第 1 轮目前只给当前 case 作为判定基准（关联 case 将来一并给出）。
后续定时程序负责：建立 case 间的关联关系；把多个 case 合并为一个大 case（父子层级由此产生）。

### 与 nexus 的边界
组件提供归档与定位能力，不接入 nexus 的 agentic loop。定位结果的消费方（输入处理器或原生工具）以及 agentic loop 内的记忆搜索工具均为后续独立实现。
