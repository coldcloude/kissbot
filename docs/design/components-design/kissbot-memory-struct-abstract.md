# kissbot-memory-struct-abstract 组件设计

## 概述

摘要记忆实现组件，是记忆结构框架（kissbot-memory-struct）的一个实现模块，作为独立服务运行。组件用大模型把原始记忆划分为事件：一个事件的记忆单独摘抄一份完整记录并生成摘要；新记忆数据经判定归档到事件，必要时自顶向下分层归并；新消息到达时先定位所属事件，取事件的摘要或原文作为上下文。

组件只负责「记忆的事件化组织与定位」，不改变原始记忆的存储，也不消费定位结果——定位结果如何进入 nexus 的上下文由后续独立实现（输入处理器或原生工具）承担。

## 核心功能

### Epic 1：新数据订阅与懒处理
- **目标**：订阅记忆存储的新数据通知并在**通道**（messenger + agent 在该通道绑定的用户 + 群组）粒度登记变化；归档计算推迟到查询时统一进行
- **依赖**：kissbot-memory-store（新数据通知服务）、kissbot-memory（原始记录的读取与索引）
- **用户故事**：
  - 作为一个外部系统（记忆存储模块），我要在写入新记录后向已连接的摘要记忆广播通知，以使摘要记忆知道有新数据
  - 作为一个外部系统（记忆存储模块），我要在通道消息的通知中给出 agent、角色与通道，以使摘要记忆能精确登记是哪个作用域哪个通道发生了变化
  - 作为一个调用方，我要在任意查询前自动完成待处理记忆的归档，以使查询结果始终反映最新记忆，而不依赖归档时机设置
  - 作为一个管理员，我要一个通道的记录只进它自己通道的批次，以使多个通道（不同 messenger / 用户 / 群组）的记忆互不吞并

### Epic 2：事件分组、归档与分层归并
- **目标**：把某通道的待处理记录交大模型按事件分组，属于当前事件的组直接并入、其余组各自归并到已有事件或新建事件节点
- **依赖**：Epic 1（待处理批次）、kissbot-llm（模型调用）
- **用户故事**：
  - 作为一个管理员，我要新记忆数据自动分组并归档到合适的事件，以使记忆按事件组织而无需人工整理
  - 作为一个管理员，我要属于当前事件的组直接并入当前事件、其他组自顶向下归并到已有事件之下，以使事件形成多层结构
  - 作为一个调用方，我要事件模式下的记忆整体归为一个事件，以使按事件隔离的上下文不被再次切分

### Epic 3：事件内容与摘要维护
- **目标**：为每个事件保存归属它的原始记录副本与大模型摘要，内容变化后重算摘要并级联更新祖先摘要
- **依赖**：Epic 2（事件与层级）、kissbot-llm（模型调用）
- **用户故事**：
  - 作为一个调用方，我要事件自包含原文副本与摘要，以使事件不受原始记录流后续变化的影响
  - 作为一个调用方，我要父事件摘要涵盖其子事件内容，以使大事件摘要完整反映其内容

### Epic 4：事件定位与上下文供给
- **目标**：给一批消息（可跨通道）定位其涉及的全部事件并给出事件标识；摘要与原文副本由调用方按需取
- **依赖**：Epic 2、Epic 3（事件内容与层级）、kissbot-llm（模型调用）
- **用户故事**：
  - 作为一个调用方，我要一次传入多条消息并取回它们涉及的全部事件标识与分组，以决定用哪些事件的记忆
  - 作为一个调用方，我要定位对每条消息都按它所在通道的当前事件比对，以使多通道消息各自命中自己的话题
  - 作为一个调用方，我要定位时新消息与已存记录去重、一并分析，以使同一条消息不被分析两次、事件归属与归档结果一致
  - 作为一个调用方，我要按事件标识分别取摘要、全部原文、指定位置之后的原文、结尾若干条原文，以按需拼装上下文而不必一次拉全量
  - 作为一个调用方，我要在消息都不涉及已有事件时得到空的事件列表，以识别话题切换

### Epic 5：事件查询与管理
- **目标**：提供事件树、事件摘要与原文副本（全部 / 指定之后 / 结尾若干条）的查询，以及手动触发与重建能力
- **依赖**：Epic 2、Epic 3
- **用户故事**：
  - 作为一个管理员，我要查询某作用域的事件树与事件摘要，以核对记忆组织是否正确（各通道水位与当前事件指针见数据目录下的状态文件）
  - 作为一个调用方，我要按位置增量续读事件的原文副本，以在不重复拉取的前提下跟进事件内容
  - 作为一个调用方，我要只取事件结尾若干条原文副本，以用最近若干条拼装上下文
  - 作为一个管理员，我要手动触发或重建某作用域的归档，以处理通知缺失或导入历史记录
  - 作为一个外部系统（记忆管理界面），我要读取事件、摘要与原文，以在界面上展示与维护

## 模块划分

- **通知订阅**：连接记忆存储的通知服务，维护长连接与重连
- **懒处理调度**：登记作用域/通道的待处理标记，查询前把该作用域各通道水位之后的记录分别成批处理；定位请求还负责把新消息与待归档记录去重后并入同一批
- **记录读取**：从共享记忆文件读取四类原始记录，并标注每条记录的通道归属（通道记录按自身身份，思考/工具记录按 key 关联的占位通道记录）
- **事件树管理**：事件节点、层级与各通道当前事件指针的读写和持久化
- **分组与落位**：第 1 轮按事件分组（并标记当前事件组），当前事件组直接并入，其余组分层下探落位（新增事件均为叶子）；批次可由待归档记录与只用于定位的新消息混合组成，只含新消息的组只读下探、不新建事件
- **摘要器**：事件摘要生成与祖先摘要级联重算
- **定位器**：按通道对一批消息做分组轮，再逐组只读下探，输出涉及的全部事件标识与分组；逐层下探与结果汇总的实现与归档器共用
- **API 服务**：对外查询、定位与管理接口（事件树/事件摘要/原文副本查询与分页/定位/手动触发/重建）
- **配置**：组件配置读取（模型 provider、分块上限、服务地址）
- **模型接入**：复用 LLM 基础库完成模型调用与会话上下文管理

## 功能流程

### Epic 1 懒处理流程
记忆存储写入新记录 → 广播通知 → 摘要记忆**只登记待处理标记**（通道消息按通道登记；思考/工具通知、首次加载、通知重连按作用域登记），不读盘、不调模型。
任意查询（定位、事件树/摘要/原文查询、手动触发）到达 → 若该作用域有待处理标记，则读一次共享记忆文件，把**每个通道**水位之后的记录各自成批（通道记录按自身身份，思考/工具记录按 key 找同 key 的占位通道记录）→ 逐批归档 → 逐块落盘。
没有待处理标记时查询不做任何额外工作；处理失败时标记保留，下次查询重试。

### Epic 2 事件归档流程
按通道取待归档批次 → 事件模式的作用域：直接并入该作用域唯一的顶层事件。
角色模式的作用域：
1. 第 1 轮（分组轮）——把该通道当前事件与全部待处理消息一起交给模型，模型按事件分组并标记哪些组属于当前事件；标记为当前事件的组直接并入当前事件，其余组以组为单位进入第 2 轮。
2. 第 2 轮起分层归并——每个组自顶层起逐层给出当层全部事件摘要，产生两种结果之一：并入某事件（该事件为叶子时内容并入，非叶子时下潜到其子层继续判定）；在本层新增叶子事件（自父事件下潜后当层未命中任何子事件时，即在该父事件下新建叶子事件）。
3. 落位后按事件聚合追加原文副本 → 重算受影响事件摘要 → 级联重算祖先摘要 → 该通道当前事件指针指向最后一批消息落入的事件。
事件树按作用域共享一棵，各通道的批次都归并到同一棵树里；当前事件指针按通道各记一份。

### Epic 3 摘要生成流程
事件内容变化 → 汇总该事件的直接记录与子事件摘要 → 模型生成摘要 → 更新节点 → 自底向上重算受影响的祖先摘要。

### Epic 4 事件定位流程
一批消息到达 → 先触发懒处理：**按通道分开调用**，该通道有待归档记录时在单通道批次内按 `msg_id` 与新消息去重（`msg_id` 为空的不参与去重、原样保留），把「已存记录 + 不重复的新消息」合并成一个批次 → 按通道分别用「该通道当前事件 + 合并批次」做第 1 轮分组（与归档同一套提示词与解析）→ 标记为当前事件的组命中该通道当前事件；其余组只读地自顶层逐层下探（命中叶子即该组事件；命中非叶子后其子层都未命中则命中该父事件；顶层未命中则该组是新话题，不涉及已有事件）→ 汇总为「消息涉及的全部事件（去重）+ 分组」。
去重部分是：重复的新消息用已存版本参与分析一次，已存记录照常落盘归档，重复的新消息与不重复的新消息都只返回所属事件、不落盘。
定位本身只读且不读原文副本：不新建、不修改事件；待归档记录引发的新事件仍由本次懒处理的分组归并完成，只含新消息的组只读下探、不新建事件。
上下文装配交给调用方：拿到标识后按需取摘要（`event/summary`）、全部原文（`event/records`）、指定位置之后的原文（`event/records-after`）或结尾若干条（`event/records-tail`）。

### Epic 5 查询与管理流程
查询请求 → 先做一次懒处理（有变化时按该作用域全部通道各归档一次）→ 事件树管理按作用域读取树与各通道当前事件指针（原文查询再读事件原文副本）→ 返回。
手动触发 → 忽略待处理标记，强制把各通道水位之后的记录处理一次。
重建请求 → 清空该作用域事件数据并复位全部通道的当前事件指针与水位 → 按共享记忆文件重新构建事件树与摘要（各通道分别处理）。

## 关键设计

### 事件树组织
事件以 (agent, 角色) 为作用域组织成一棵树，跨年份持续累积；大事件可以包含子事件。每个事件保存归属它的原始记录副本与大模型摘要，内容自包含。父事件摘要由自身直接记录与子事件摘要合成。
归档只新建叶子事件；父子层级由后续「建立事件间关联关系」与「把多个事件合并为大事件」的定时程序产生（预留），因此分层归并的下潜分支在当前阶段不会被触发。

### 按通道隔离的记忆流
事件树按作用域组织（同一角色的记忆是一棵树），而「最近被并入内容的事件」（当前事件指针）与「已处理水位」按通道各记一份：通道 = `messenger_id + self_user_id + group_id`（agent 在该通道绑定的用户 + messenger + 群组），发送者 `user_id` 不参与——本人消息与对话对方的消息因此属于同一通道。
查询时按通道分别切出待处理记录、各自成批归档、各自推进水位，一个通道的归档不影响其他通道；定位时用新消息的通道取当前事件指针。归档与定位都**按通道分开调用**，批次内只有该通道的记录与消息（这也是判重只看 `msg_id` 的前提）。这样同一角色同时服务多个通道时，各通道的归档互不吞并、上下文互不串味。

### 两种记忆来源
- **角色模式**：作用域内的记录经模型判定切分为事件，可多层归并。
- **事件模式**：作用域整体对应一个顶层叶子事件，内部不再划分，也不参与分层归并。

### 当前事件优先
每个通道维护一个当前事件指针，指向该通道最近被并入内容的事件。归档与定位都用同一套分组轮：把**该通道**的当前事件与消息一起交给模型，由模型标记哪些消息属于当前事件——标记的组直接命中，其余才扩大到更大范围（逐层下探），以落实「优先选择当前事件」并控制调用开销。

### 归档以通道为准
批次按通道切分：通道记录按自身身份归属，思考与工具记录按自身的 key 找到同 key 的思考/工具占位通道记录后归属到对应通道，随该通道的批次一并归档，使事件完整保留推理与行动轨迹；找不到占位记录的记录不属于任何通道，也不进入任何批次。

### 懒处理：通知只登记，查询才计算
通知只回答「哪个作用域哪个通道有新数据」，不做任何计算；归档在查询前统一进行（查询的作用域内所有通道各算一次）。这样既不依赖任何归档时机规则（无超时、无本人/非本人消息判定），也不会因为长时间无人查询而积累「必须靠定时任务才能收尾」的尾巴；代价是查询会承担归档开销，因此用待处理标记做闸门，没有变化时不读盘、不调模型。

### 定位与懒处理合并：新消息与已存记录去重
定位也是查询，会先触发懒处理。归档与定位都**按通道分开调用**：若此时该通道还有水位之后的待归档记录，而定位请求的消息又往往正是这些记录，分两次分析会让同一条消息参与两次判定、事件归属还可能不一致。因此定位把该通道的待归档记录与本批新消息**去重后合并**为一个批次，只做一次分组轮：批次已按通道切分，判重只比 `msg_id`（消息标识来自 incoming_message / outgoing_message_response，思考/工具占位记录为空；为空的一律不参与去重、原样保留），重复的新消息用已存版本参与分析，其余新消息随批次参与分析但不落盘；已存记录照常归档，新消息只返回所属事件。只含新消息的组不下潜新建事件——定位不产生记忆，新事件的建立仍由归档完成。

### 分组由模型决定，批次边界不再由规则切分
第 1 轮把当前事件与整批待处理消息一起交给模型，让模型按事件分组并标记当前事件组：属于当前事件的组直接并入，其他组各自作为独立单元进入分层归并。批次边界由此由内容决定，而不是由「本人消息 / 超时」这类时间与身份规则切分。定位触发时批次是「待归档记录 + 去重后的新消息」的合并结果，对模型而言仍是同一个按时间排列的消息流。

### 分级候选控制上下文规模
第 1 轮只给**该通道的当前事件**摘要（外加待处理消息本身），第 2 轮起才逐层给出当层全部事件摘要，避免一次把全部事件摘要送入模型。
待处理消息按 `max_batch_records` 分块（定位触发时按合并后的批次分块），保证单次送入模型的消息量有界。

### 模型接入
模型调用与会话上下文复用 LLM 基础库，会话按事件作用域隔离；组件自身持有 provider 配置，不读取 agent 的配置。

### 关联事件与事件合并（预留）
事件之间的关联关系、关系描述，以及关联事件摘要纳入上下文，留待后续实现；第 1 轮目前只给当前事件作为判定基准（关联事件将来一并给出）。
后续定时程序负责：建立事件间的关联关系；把多个事件合并为一个大事件（父子层级由此产生）。

### 与 nexus 的边界
组件提供归档与定位能力，不接入 nexus 的 agentic loop。定位结果的消费方（输入处理器或原生工具）以及 agentic loop 内的记忆搜索工具均为后续独立实现。
