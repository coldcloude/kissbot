# kissbot-memory-struct-summary 组件设计

## 概述

摘要记忆是记忆结构的一种实现，作为独立服务运行。它把原始记忆切分为 **case（专案）**，为每个 case 保存归属它的原文副本与大模型生成的摘要，并按新消息定位其所属 case，向调用方提供 case 摘要与原文片段。

case 是本组件对记忆的切分与归并产物，与 agent 侧的 **event（事件）** 不同：event 是记忆范围的划分，case 是记忆内容的组织。一个「agent + 角色」拥有一片 case 森林，角色模式的 case 与各事件模式的 case 都组织在这片森林里，靠路径首段区分。组件只负责 case 化组织与定位，不改变原始记录的存储，也不决定定位结果如何进入对话上下文。

## 核心功能

### Epic 1：新数据登记与按需处理

- **目标**：订阅记忆存储的新数据通知，按「记忆范围 + 通道」登记待处理，把归档计算推迟到显式入口
- **依赖**：kissbot-memory-store（通知服务与共享文件）、kissbot-memory（记录读取）
- **用户故事**：
  - 作为一个外部系统（记忆存储服务），我要在写入新记录后广播位置，以让摘要记忆知道哪个范围哪个通道有新数据
  - 作为一个调用方，我要让通知只做登记、不做计算，以使归档不在写入路径上发生
  - 作为一个调用方，我要一次只处理一个通道的新数据，以使不同通道的记忆互不吞并
  - 作为一个管理员，我要能手动触发一次归档，以在通知缺失时补齐处理

### Epic 2：case 归档与摘要

- **目标**：把待归档记录按声明的 case 落位，为叶子 case 生成摘要并自底向上更新祖先摘要，推进处理水位
- **依赖**：Epic 1、kissbot-llm（模型调用）
- **用户故事**：
  - 作为一个调用方，我要在写入记录时声明其所属 case，以使归档不重新判定
  - 作为一个管理员，我要每个 case 自包含原文副本与摘要，以使 case 不受原始记录流后续变化的影响
  - 作为一个管理员，我要父 case 的摘要涵盖其子 case，以使大 case 的摘要完整反映其内容
  - 作为一个管理员，我要没有 case 声明的记录被跳过而非被猜测归类，以使归档结果可预期

### Epic 3：新消息定位

- **目标**：给同一通道的一批新消息定位其涉及的 case，同一 case 只返回一组；定位与落地分离，定位阶段不改动 case 森林
- **依赖**：Epic 2、kissbot-llm
- **用户故事**：
  - 作为一个调用方，我要一次传入同一通道的多条消息并取回它们涉及的 case，以决定用哪些 case 的记忆
  - 作为一个调用方，我要定位优先命中该通道的当前 case，以控制模型调用开销
  - 作为一个调用方，我要新话题也能得到一个 case 名，以使后续写入记录能直接落位
  - 作为一个调用方，我要事件模式直接归入该事件的根 case，以使按事件隔离的上下文不会被再次切分

### Epic 4：case 查询与重建

- **目标**：提供 case 森林、case 摘要、原文副本（整份 / 指定位置之后 / 结尾若干条）的只读查询，以及清空后重建的能力
- **依赖**：Epic 2、Epic 3
- **用户故事**：
  - 作为一个管理员，我要查询某个角色的 case 森林与各通道的当前 case，以核对记忆组织是否正确
  - 作为一个调用方，我要按位置增量续读 case 的原文副本，以在不重复拉取的前提下跟进内容
  - 作为一个调用方，我要只取 case 结尾若干条原文，以拼装对话上下文
  - 作为一个管理员，我要重建某个记忆范围的 case，以在处理逻辑变更或数据导入后重新组织

## 模块划分

- **通知订阅**：连接记忆存储的通知服务，维护长连接与重连，重连后补登记
- **角色状态管理**：按「agent + 角色」维护 case 森林、各通道的当前 case 指针与水位、待处理标记，并负责状态文件的读写
- **记录读取**：直接读取记忆存储的共享文件，按通道水位切出待归档记录
- **归档器**：按 case 落位记录、生成叶子摘要、级联更新祖先摘要、推进水位；失败时回滚状态
- **定位器**：分组轮与逐层判定，产出「消息 → case」的分组，并在落地阶段建出新 case
- **模型接入**：复用 LLM 基础库完成分组、逐层判定与摘要生成，判定会话按记忆范围隔离
- **查询与管理接口**：case 森林、摘要、原文、定位、手动触发与重建
- **配置**：监听地址、通知地址、单次定位分块上限、会话保留条数、模型与生成参数

## 功能流程

### 新数据登记流程

```
记忆存储写入完成并广播
  → 收到通知：打开对应角色（首次打开时加载 case 森林）
  → 只登记「该记忆范围该通道有待处理数据」
  → 不读文件、不调模型
通知连接（重）建立
  → 把已加载角色在存储中出现过的全部记忆范围登记为待处理
```

### 归档流程（某记忆范围 × 某通道）

```
取该通道水位之后的待归档记录
  → 逐条读取其声明的 case：
      ├─ 没有声明或路径非法：跳过（水位照常前进）
      └─ 有声明：case 不存在则按路径逐段建出（祖先为复合、末段为叶子）
  → 按 case 聚合记录
  → 为每个受影响的叶子 case 生成新摘要（当前摘要 + 本批记录）
  → 更新记录条数与起止时间
  → 按深度从深到浅重算受影响的复合 case 摘要（当前摘要 + 各子摘要）
  → 全部成功后一次性提交：追加原文副本、推进水位、更新当前 case 指针、落盘状态
  → 任一步失败：回滚状态，磁盘保持不变，标记保留待下次重试
```

### 定位流程（某通道的一批新消息）

```
先对本通道做一次归档（见上）
  → 角色模式：
      取出该通道的当前 case
      → 第 1 轮：把本批消息按 case 分组，并标出属于当前 case 的组（必须完整覆盖本批消息）
      → 标记为当前的组直接归入当前 case
      → 其余组按组内首条消息时间顺序逐个处理：
          从角色树顶层开始，把当层候选（名称与摘要）与该组内容交给模型
            ├─ 名称命中当层叶子：归入该 case，结束
            ├─ 名称命中当层复合 case：下潜一层继续
            └─ 未命中任何候选：在当层新建叶子 case，结束
  → 事件模式：跳过第 1 轮，直接以该事件的根 case 为目标（叶子则整体归入，复合则继续逐层判定）
  → 落地：命中的 case 直接使用，新建的 case 只建出节点（不生成摘要、不写原文）
  → 更新当前 case 指针为本批最后一条有落点的消息所属 case
  → 返回「case → 消息标识集合」的分组
```

### 查询与重建流程

```
查询：按记忆范围与父 case 读取森林的一层 / 读取某个 case 的节点 / 读取原文副本
      → 只读，不触发归档，也不清除待处理标记
手动触发：忽略待处理标记，把该范围各通道水位之后的记录全部处理一次
重建：先清空本次记忆范围自己的 case（角色模式清该角色的全部角色 case；事件模式清该事件的整棵子树）
      → 复位该范围的指针与水位
      → 按记录中声明的 case 重新落位并生成摘要
```

## 关键设计

### 两级归属

「agent + 角色」决定 case 森林，同一角色的角色模式与所有事件模式共用这一片森林；「角色 + 可选事件」决定输入与状态，原始记录读取范围、水位与当前 case 指针都按记忆范围区分。这样 case 的组织与事件的划分互不干扰：切换事件不改变 case 森林，重建某个事件也不影响角色模式与其他事件。

### case 森林结构

角色模式一棵树，固定根隐藏且不是业务 case，其子节点是角色顶层 case；每个事件一棵树，根是可见的业务 case。叶子 case 持有原文副本与摘要，复合 case 只由子 case 组成，摘要由子摘要合成。原始记录只能写入叶子 case，指向非叶子时跳过该部分记录。

### 完整路径即标识

case 的唯一标识是相对森林的完整路径，同一父下同名即同一个 case，不同父下同名靠路径区分。模型只负责给出「当层的一个名称」，路径由本组件拼接；事件根的名称是固定的查找键，不参与模型判定。这样模型看到的始终只是当层的候选名，不需要理解整棵树。

### 声明式的落位

写入方可以把消息所属 case 直接写进记录的元信息。归档时优先按元信息落位，不走分组与逐层判定，只重算摘要；没有元信息的记录跳过。这样主链路的模型调用只发生在「新消息定位」一次，重复归档不会因历史记录而反复消耗模型。

### 判定与落地分离

定位阶段只读：分组与逐层判定不建 case、不改森林、不落盘。落地阶段才创建节点、更新指针。两者分离使「定位失败」与「归档失败」的影响范围清楚：定位失败不影响已有 case，归档失败可以整体回滚。

### 通道隔离

水位、当前 case 指针与待处理标记都按「记忆范围 + 通道」维护，一次处理只覆盖请求的通道。通道由 messenger、接收方用户与群组确定，发送者不参与，因此对话双方的消息属于同一通道。这样同一角色服务多个通道时，各通道的记忆不会互相吞并，也不会串味。

### 按请求计算

通知只登记，真正的计算只发生在定位、手动触发与重建。组件没有定时器，也不需要为「何时归档」设计时间规则；归档的触发点由调用方的请求节奏决定。

### 覆盖性与失败回滚

分组结果必须完整覆盖本批消息，缺任何一条都按失败处理，避免后续写入的记录被水位跳过。归档在全部计算完成后一次性提交，任一步失败都回滚状态，磁盘保持上一次成功的状态。

### 角色级串行

同一角色的归档、定位、重建与查询按顺序执行，不同角色可以并行。这保证了在同一片森林上不会出现并发改写；代价是某一角色的慢模型调用会阻塞该角色的其他请求。

### 模型会话按记忆范围隔离

判定与摘要使用的模型会话按记忆范围区分，同一范围内的连续判定共享上下文，从而让模型看到自己此前的判断；上下文超过保留条数时归档并裁剪，避免无限增长。
