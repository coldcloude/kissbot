# kissbot-memory-struct-summary 组件设计

## 概述

摘要记忆实现组件，是记忆结构框架（kissbot-memory-struct）的一个实现模块，作为独立服务运行。组件用大模型把原始记忆划分为 **case（专案）**：一个 case 的记忆单独摘抄一份完整记录并生成摘要；新记忆数据经判定归档到 case，必要时自顶向下分层归并；新消息到达时先定位所属 case，取 case 的摘要或原文作为上下文。

这里的 case 是本组件对记忆切分与归并的产物，与 agent 侧 role-event 的 **event（事件）** 区分：case 森林以一个 **`AgentRole { agent_id, role }`** 为归属——角色模式一棵树（隐藏的固定根 `__role_root__`，其子节点是角色 case），每个事件一棵树（根是 `event-{事件标识}`）；角色模式的 case 由模型判定划分，事件模式由 `event_id` 直接在森林里定位事件根（叶子时整体归入，非叶子时以它为根继续下潜）。case 节点不记录模式或事件信息；原始记录只能写入叶子 case。

组件只负责「记忆的 case 化组织与定位」，不改变原始记忆的存储，也不消费定位结果——定位结果如何进入 agent 的上下文由 agent 侧的摘要记忆 pipeline 承担。

## 核心功能

### Epic 1：新数据订阅与懒处理
- **目标**：订阅记忆存储的新数据通知并在「记忆后缀 + 通道」（通道 = messenger + agent 在该通道绑定的用户 + 群组）粒度登记变化；归档计算推迟到查询时统一进行
- **依赖**：kissbot-memory-store（新数据通知服务）、kissbot-memory（原始记录的读取与索引）
- **用户故事**：
  - 作为一个外部系统（记忆存储模块），我要在写入新记录后向已连接的摘要记忆广播通知，以使摘要记忆知道有新数据
  - 作为一个外部系统（记忆存储模块），我要在通道消息的通知中给出 agent、记忆后缀与通道，以使摘要记忆能精确登记是哪个后缀哪个通道发生了变化
  - 作为一个调用方，我要一个显式的手动触发归档入口（以及在定位时顺带处理本通道待归档记录），以在需要时让结果反映最新记忆，而不依赖隐藏的时机规则
  - 作为一个管理员，我要一个通道的记录只进它自己通道的批次，以使多个通道（不同 messenger / 用户 / 群组）的记忆互不吞并

### Epic 2：case 分组、归档与分层归并
- **目标**：把某通道的待处理记录交大模型按 case 分组，属于当前 case 的组直接并入、其余组各自归并到已有 case 或新建 case 节点
- **依赖**：Epic 1（待处理批次）、kissbot-llm（模型调用）
- **用户故事**：
  - 作为一个管理员，我要新记忆数据自动分组并归档到合适的 case，以使记忆按 case 组织而无需人工整理
  - 作为一个管理员，我要属于当前 case 的组直接并入当前 case、其他组自顶向下归并到已有 case 之下，以使 case 形成多层结构
  - 作为一个管理员，我要角色模式的逐层判定只取 `role-` 前缀的角色 case（`event-` 前缀的事件叶子不参与），以使事件模式的固定 case 不被并入角色 case
  - 作为一个调用方，我要事件模式下的记忆整体归入事件根（叶子时直接归入、非叶子时下潜），以使按事件隔离的上下文不被再次切分

### Epic 3：case 内容与摘要维护
- **目标**：为每个 case 保存归属它的原始记录副本与大模型摘要，内容变化后重算摘要并级联更新祖先摘要
- **依赖**：Epic 2（case 与层级）、kissbot-llm（模型调用）
- **用户故事**：
  - 作为一个调用方，我要 case 自包含原文副本与摘要，以使 case 不受原始记录流后续变化的影响
  - 作为一个调用方，我要父 case 摘要涵盖其子 case 内容，以使大 case 摘要完整反映其内容

### Epic 4：case 定位与上下文供给
- **目标**：给同一通道的一批消息定位其涉及的 case 并给出 case 名（同一 case 只返回一组）；摘要与原文副本由调用方按需取
- **依赖**：Epic 2、Epic 3（case 内容与层级）、kissbot-llm（模型调用）
- **用户故事**：
  - 作为一个调用方，我要一次传入同一通道的多条消息并取回它们涉及的分组，以决定用哪些 case 的记忆
  - 作为一个调用方，我要定位按请求给出的通道的当前 case 比对，以使不同通道的消息各自命中自己的话题
  - 作为一个调用方，我要在写入记忆时附上消息所属的 case，以使组件下次归档时直接按 case 名定位，不必重新分组判定
  - 作为一个调用方，我要按 case 名分别取摘要、全部原文、指定位置之后的原文、结尾若干条原文，以按需拼装上下文而不必一次拉全量
  - 作为一个调用方，我要新话题也有 case 名（本次建出、记忆条数为 0），以使同一话题后续写入记忆时并入同一 case

### Epic 5：case 查询与管理
- **目标**：提供 case 树、case 摘要与原文副本（全部 / 指定之后 / 结尾若干条）的查询，以及手动触发与重建能力
- **依赖**：Epic 2、Epic 3
- **用户故事**：
  - 作为一个管理员，我要查询某角色的 case 树与该记忆后缀的 case 摘要，以核对记忆组织是否正确（各通道水位与当前 case 指针见数据目录下的状态文件）
  - 作为一个调用方，我要按位置增量续读 case 的原文副本，以在不重复拉取的前提下跟进 case 内容
  - 作为一个调用方，我要只取 case 结尾若干条原文副本，以用最近若干条拼装上下文
  - 作为一个管理员，我要手动触发或重建某记忆后缀的归档，以处理通知缺失或导入历史记录
  - 作为一个外部系统（记忆管理界面），我要读取 case、摘要与原文，以在界面上展示与维护

## 模块划分

- **通知订阅**：连接记忆存储的通知服务，维护长连接与重连
- **归档调度**：登记「记忆后缀 + 通道」的待处理标记；定位**只处理请求通道**（该通道水位之后的记录 + 本批消息），手动触发与重建才逐通道处理全部通道；带摘要记忆 meta 的记录直接落到指定 case（meta 指向的 case 缺失时建出），没有 meta 的记录跳过；只有定位请求的本批新消息按通道做分组与逐层判定
- **记录读取**：读取通道记录；思考/工具内容内嵌在记录的 `content` 里，随所属通道记录一起读取
- **case 树管理（`AgentRoleManager` / `AgentRoleHandle` / `AgentRoleState`）**：按 AgentRole 组织 case 节点与层级，按记忆后缀记录各通道的当前 case 指针、水位与待处理标记，并负责读写与持久化
- **归档器**：按通道把「水位之后的记录 + 可选的只用于定位的新消息」按时间合并后分块处理——带 meta 的记录直接落指定 case（缺失则建出、追加记录、摘要级联），无 meta 的记录跳过；只有新消息先只读定位（逐组判定落点），再逐组落地（新建 case，记录条数为 0）
- **分组与落位**：第 1 轮按 case 分组（并标记当前 case 组），当前 case 组直接并入，其余组逐层判定落点（归入已有 case / 需要新建）；判定不改树，新消息组一律命中或建出 case（只定位的组记忆条数为 0）
- **摘要器**：case 摘要生成与祖先摘要级联重算
- **逐层判定与结果汇总**：分组后逐组判定落点（判定只读、不改树；新消息组一律命中或建出 case），并把同一 case 的多个组按消息 `msg_id` 合并成一组返回
- **API 服务**：对外查询、定位与管理接口（case 树/case 摘要/原文副本查询与分页/定位/手动触发/重建）
- **配置**：组件配置读取（模型 provider、分块上限、服务地址）
- **模型接入**：复用 LLM 基础库完成模型调用与会话上下文管理，会话按 `(AgentRole, event_id)` 隔离

## 功能流程

### Epic 1 懒处理流程
记忆存储写入新记录 → 广播通知 → 摘要记忆**只登记待处理标记**（通道消息按「记忆后缀 + 通道」登记；思考/工具通知、后缀未知通道、首次加载、通知重连按该后缀全部通道登记），不读盘、不调模型。
处理入口只有两种：`locate`（带本批消息）、`/summary/rebuild` 的 rebuild=false（手动触发）与 rebuild=true（重建）→ 读一次共享记忆文件，把**每个通道**水位之后的通道记录各自成批（思考/工具内容内嵌在记录里，随记录归属该通道）→ 逐批归档 → 逐块落盘。case 森林/摘要/原文查询只读，不触发归档。
没有待处理标记时查询不做任何额外工作；处理失败时标记保留，下次查询重试。

### Epic 2 case 归档流程
按通道取待归档批次 → 事件模式的记忆后缀：由 `event_id` 直接定位（不存在则建出）事件根 `event-{事件标识}`；事件根是叶子时直接归入，非叶子时以它为根下潜（新子 case 为 `event-{事件标识}-{名称}`），不调分组轮。
角色模式的记忆后缀（同一 AgentRole 的 case 森林）：
1. 第 1 轮（分组轮）——把该通道当前 case 与本批新消息一起交给模型，模型按 case 分组并标记哪些组属于当前 case。输入是**按消息**组织的固定格式 JSON（`msg_id` / `time` / `user_id` / `content`）：一条消息一条原文，思考/工具内容以标签内嵌在所属消息的 `content` 里、不单独成条；输出是每组原文消息的 `msg_id` 列表（每条恰好一次，不要求连续）。标记为当前 case 的组直接并入当前 case，其余组以组为单位进入第 2 轮；组按组内**首条记忆的时间顺序**处理。
2. 第 2 轮起逐层判定——每个组自顶层起逐层给出当层全部**角色 case** 摘要，产生两种结果之一：并入某 case（该 case 为叶子时内容并入，非叶子时下潜到其子层继续判定）；新建叶子 case（当层未命中时在该层新建；只含新消息的组也建，记忆条数为 0）。事件模式的固定 case 不在候选里，两种模式互不并入。
3. 落地后按 case 聚合追加原文副本 → 重算受影响 case 摘要 → 级联重算祖先摘要 → 该通道当前 case 指针指向本批最晚一条消息落入的 case。
case 森林按 **`AgentRole`** 归属一片，同一 AgentRole 的角色模式与事件模式都归并到同一片森林里（节点不记录模式信息）；当前 case 指针按「记忆后缀 + 通道」各记一份。

### Epic 3 摘要生成流程
case 内容变化 → 叶子 case 取**当前摘要 + 本批全部待归档记录**，复合 case 取**当前摘要 + 子 case 摘要** → 模型生成摘要 → 更新节点 → 自底向上重算受影响的祖先摘要。归档不再读取全部历史记录，也不再重新定位。

### Epic 4 case 定位流程
一批消息到达（定位只处理请求通道）→ ① 提取：读一次该记忆后缀的共享记忆取出请求通道水位之后的待归档消息（pending，思考/工具内容内嵌在消息里）与本批消息（两者都可为空）→ ② 定位：带摘要记忆 meta 的 pending 记录直接落到指定 case（不调模型；case 缺失时按 meta 建出），没有 meta 的 pending 直接跳过并推进水位；本批新消息按时间合并成一个批次（新消息在 locate 时尚未写入记忆，无需按 `msg_id` 去重）；角色模式用「该通道当前 case + 本批新消息」做第 1 轮分组，再逐组判定落点——标记为当前 case 的组命中该通道当前 case，其余组自顶层逐层判定（命中叶子即该组 case；命中非叶子后其子层都未命中则命中该父 case；顶层未命中则该组是新话题）→ ③ 落地 + 存储 + 返回：新消息逐组建出/命中 case（新话题一律建出叶子 case，记忆条数为 0）；带 meta 的 pending 记录按 meta 追加原文副本、重算摘要、推进水位并更新当前指针；最后把同一 case 的多个新消息组按消息 `msg_id` 取并合并成一组返回（分组只给 case 名与消息 `msg_id`，不对分组与消息排序）。
事件模式不分组：整个后缀归入 `event-{事件标识}` 事件根；事件根不存在则建出叶子（记忆条数为 0），非叶子时以它为根下潜，新子 case 为 `event-{事件标识}-{名称}`。
**pending 记录不参与判定**：带 meta 的直接落 case（case 缺失则建出），没有 meta 的跳过；判定只针对本批新消息，结果只有「归入某已有 case」和「需要新建在某父 case 之下」两种，两者都会命中或建出 case（新消息不落盘）。
只要调用 locate，输入就是「pending + 消息」，没有「先归档再定位」的两段式，也没有第二轮补齐循环；`messages` 为空时（手动触发 / 重建）即按 meta 归档，带 meta 的记录落盘、无 meta 跳过，不返回消息结果。
角色树里还没有角色 case 时当层候选为空，逐层判定照常调用模型（由它给出新 case 的名称与摘要），第 1 轮分组后每个组建出记忆条数为 0 的 case；事件模式下 `event-{事件标识}` 这个事件根不存在时也建出（叶子）。
上下文装配交给调用方：拿到标识后按需取摘要（`case/summary`）、全部原文（`case/records`）、指定位置之后的原文（`case/records-after`）或结尾若干条（`case/records-tail`）。

### Epic 5 查询与管理流程
查询请求 → 直接由 case 森林管理按角色读取森林、按记忆后缀读取各通道当前 case 指针（原文查询再读 case 原文副本）→ 返回；**查询只读，不触发归档**。需要处理待归档记录时由调用方显式调 `/summary/rebuild` 的 rebuild=false（或走定位）。
手动触发 → 忽略待处理标记，强制把该后缀各通道水位之后的记录处理一次。
重建请求 → **只清空本次记忆后缀自己的 case**（角色模式清空该 AgentRole 树里全部 `role-` 前缀的角色 case；事件模式只清本后缀固定的 `event-{事件标识}` 叶子，同一 AgentRole 的其他事件后缀不受影响）+ 该后缀的指针/水位，再按共享记忆文件重新构建（各通道分别处理）。

## 关键设计

### case 森林组织
case 森林以一个 **`AgentRole { agent_id, role }`** 为归属，跨年份持续累积；一个 AgentRole 的森林由角色树（隐藏固定根 `__role_root__` + 角色 case）与每个事件一棵树（根 `event-{事件标识}`）组成。叶子 case 保存归属它的原始记录副本与大模型摘要，内容自包含；复合 case 只由子 case 组成，摘要由子 case 摘要合成。原始记录只能写入叶子 case，meta 或定位结果指向非叶子时按失败处理。
**同一 AgentRole 的角色模式与事件模式共用这一片森林**（同一个 `AgentRoleHandle`、同一个目录），但各走各的子树：角色模式的新 case 名为 `role-{模型给出的名称}`（名称只含英文字母、数字与 `-`，重名时追加 `-2`、`-3`…）；事件模式由 `event_id` 直接定位事件根（名为 `event-{事件标识}`，这是命名约定与查找键，不是节点字段），不存在则建出；事件根非叶子时以它为根逐层下潜，新子 case 为 `event-{事件标识}-{模型名称}`。两种 case 共用森林、靠名称前缀区分（角色 `role-`、事件 `event-`），节点不记录模式字段；角色模式逐层判定的当层候选只取 `role-` 前缀的 case，两种模式互不并入。新建 case 时同一次判定就给出名称与摘要，不留到后续再调模型。角色根只用于遍历，不出现在 `case/list`/`tree/get`/`case_count` 里。
归档只新建叶子 case；父子层级由后续「建立 case 间关联关系」与「把多个 case 合并为大 case」的定时程序产生（预留），因此分层归并的下潜分支在当前阶段不会被触发。

### 两级归属：AgentRole 决定树，记忆后缀决定输入与状态
- **角色（`AgentRole { agent_id, role }`）**决定 case 森林：一个 AgentRole 一片森林，同一 AgentRole 的角色模式与事件模式共用同一个 `AgentRoleHandle`（同一个目录、同一份 `AgentRoleState`）；`AgentRoleManager` 按 AgentRole 缓存句柄。
- **记忆后缀（项目级基础类型 `RoleEvent { role_name, event_id }`）**决定输入与状态：`event_id` 缺省为角色模式、给出事件标识为事件模式。拼接文件后缀是 memory 内部的事（kissbot-memory 统一负责），对外通信一律传 `RoleEvent`，调用方不再手工拼接。原始记录读取、水位、当前 case 指针都按后缀区分。
- **`event_id` 是组件内部的独立参数**：一次调用由 `agent_role`（找到对应的 case 森林）与 `event_id: Option<ArcStr>`（决定模式、决定如何查找 case）两个参数表达；模型会话按 `(AgentRole, event_id)` 隔离，同一后缀的连续判定共享上下文。

### 按通道隔离的记忆流
case 森林按 **AgentRole** 组织（一个 AgentRole 的记忆是一片森林：角色树 + 每个事件一棵树），而「最近被并入内容的 case」（当前 case 指针）与「已处理水位」按「记忆后缀 + 通道」各记一份：通道 = `messenger_id + self_user_id + group_id`（agent 在该通道绑定的用户 + messenger + 群组），发送者 `user_id` 不参与——本人消息与对话对方的消息因此属于同一通道。
查询时按通道分别切出待处理记录、各自成批归档、各自推进水位，一个通道的归档不影响其他通道；定位时用新消息的通道取当前 case 指针。归档与定位都**按通道分开调用**，批次内只有该通道的记录与消息（这也是判重只看 `msg_id` 的前提）。这样同一 AgentRole 同时服务多个通道时，各通道的归档互不吞并、上下文互不串味。

### 两种记忆来源
- **角色模式**（`RoleEvent.event_id` 缺省）：该 AgentRole 树内的记录经模型判定切分为 case，可多层归并。
- **事件模式**（`RoleEvent.event_id` 给出事件标识）：整个后缀固定对应事件根（由 `event_id` 定位 `event-{事件标识}`）；根是叶子时内部不再划分，非叶子时以它为根继续下潜，不参与角色模式的分层归并。

### 当前 case 优先
每个「记忆后缀 + 通道」维护一个当前 case 指针，指向该通道最近被并入内容的 case。归档与定位都用同一套分组轮：把**该通道**的当前 case 与消息一起交给模型，由模型标记哪些消息属于当前 case——标记的组直接命中，其余才扩大到更大范围（逐层下探），以落实「优先选择当前 case」并控制调用开销。

### 归档以通道为准
批次按通道切分：通道记录按自身身份归属，思考与工具内容内嵌在记录里、随该通道的批次一并归档，使 case 完整保留推理与行动轨迹。

### 归档时机：通知只登记，定位、手动触发与重建才计算
通知只回答「哪个记忆后缀哪个通道有新数据」，不做任何计算；归档只在**显式入口**发生：定位（带本批消息，顺带处理该后缀各通道的 pending）、`/summary/rebuild` 的 rebuild=false（手动触发）、rebuild=true（重建）。这样既不依赖任何隐藏的归档时机规则（无超时、无本人/非本人消息判定），查询也不必承担归档开销——case 森林/摘要/原文查询是纯读。待处理标记只影响「有没有新数据要处理」，没有标记且没有消息时才不读盘、不调模型。

### 定位就是「pending + 消息」的一次归档：判定与落地分开
定位不再「先归档待处理记录、再单独定位消息」，也不是「有待处理标记才归档、否则走另一条只读路径」，而是**一条路径**：
1. **提取**：读一次共享记忆，取出该记忆后缀各通道水位之后的待归档记录（pending），与本批消息一起**按通道分组**（pending 与本批消息都可为空）。
2. **定位（只读）**：每个通道调用同一个归档入口 `archive(待归档消息, 消息)`——带 meta 的 pending 记录直接按 case 名落位（不调模型，case 缺失时留到落地阶段建出），没有 meta 的 pending 记录跳过；只有新消息按时间合并成一个批次（定位发生在写入新消息之前，不需要按 `msg_id` 去重），角色模式做第 1 轮分组后**逐组判定落点**：`归入某已有 case` 或 `需要新建在某父 case 之下`；事件模式固定归入 `event-{事件标识}`。判定完全不改树。
3. **落地 + 存储 + 返回**：新消息逐组建出/命中 case——新话题一律建出叶子 case（记忆条数为 0，便于这些消息之后写入记忆时并入同一 case），新消息不落盘；带 meta 的 pending 记录追加原文副本、重算摘要、推进水位、更新当前指针（meta 指向的 case 缺失时在此建出）。最后把同一 case 的多个新消息组按消息 `msg_id` 取并合并成一组返回。

没有两个驱动：只要调用 locate，输入就是「pending + 消息」。没有待处理标记且没有消息（纯查询且无变化）时才不读盘；带消息时总会读一次共享记忆提取 pending，因此漏掉通知也能在下一次定位时被顺带归档。

分块、逐块落盘与摘要级联都由归档器承担（记录按 `max_batch_records` 分块），因此同一条入口既能在带消息时返回定位结果，也能在没有消息时单独当作归档使用（手动触发 / 重建）。

### 分组由模型决定，批次边界不再由规则切分
第 1 轮把当前 case 与本批新消息一起交给模型，让模型按 case 分组并标记当前 case 组：属于当前 case 的组直接并入，其他组各自作为独立单元进入分层归并。批次边界由此由内容决定，而不是由「本人消息 / 超时」这类时间与身份规则切分。定位触发时批次只有新消息；待归档记录按 meta 直接落 case（无 meta 跳过），不进入模型。事件模式不分组。

### 分级候选控制上下文规模
第 1 轮只给**该通道的当前 case**摘要（外加本批新消息），第 2 轮起才逐层给出当层全部**角色 case** 摘要，避免一次把全部 case 摘要送入模型。
新消息按 `max_batch_records` 分块，保证单次送入模型的消息量有界；待归档记录不参与分组，只按 meta 直接落位。逐层判定没有层数上限（每判定一次要么落在当层，要么下潜一层；case 森林有限且无环，下潜必然终止）。

### 模型接入
模型调用与会话上下文复用 LLM 基础库，会话按 `(AgentRole, event_id)` 隔离（同一 AgentRole 下角色模式与事件模式各自一个会话）；组件自身持有 provider 配置，不读取 agent 的配置。

### 关联 case 与 case 合并（预留）
case 之间的关联关系、关系描述，以及关联 case 摘要纳入上下文，留待后续实现；第 1 轮目前只给当前 case 作为判定基准（关联 case 将来一并给出）。
后续定时程序负责：建立 case 间的关联关系；把多个 case 合并为一个大 case（父子层级由此产生）。

### 与 nexus 的边界
组件提供归档与定位能力，不接入 agent 的 agentic loop。定位结果的消费方是 agent 的摘要记忆 pipeline（`memory_summary`）：它用 case 摘要与结尾原文重建上下文，并在写入记忆时填入 `meta.memory_summary.case_name`；agentic loop 内的记忆搜索工具仍为后续独立实现。
