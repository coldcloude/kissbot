# 系统设计

## 概述

kissbot 是一个可长期运行、持续积累记忆的智能体系统。它以 agent 为活动单元，把「思考」「行动」「记忆」「通信」拆分为相互独立的组件：agent 负责驱动模型对话与工具调用，消息通道负责与外部通信工具对接，记忆系统负责保存与组织历史，管理界面与公共基础库提供配置、认证与契约支持。

## 一、组件体系

### 1. 智能体（kissbot-agent）

系统的核心运行组件，由两个内部模块组成：

- **Nexus**：智能体的「思考」部分。装配并运行 pipeline，把外部输入加工为模型可用的上下文，驱动模型回复与工具调用，并把对话写入记忆系统。
- **Station**：智能体的「行动」部分。持有工具并提供工具调用能力，本身是一个 MCP 服务端，也可以把其他 Station 作为子节点级联接入。

Agent 以独立进程运行，同时对外提供管理 API 与 station 的 MCP 端点。一个 agent 可以有多个角色，每个「agent + 角色」组合对应一条 pipeline，各自拥有独立的会话上下文、记忆范围与当前事件。详见 [system-design-agent](system-design-agent.md)。

### 2. 消息通道（kissbot-channel、kissbot-channel-client、kissbot-channel-web）

连接外部通信工具的桥梁，分为服务端框架、客户端库与通道实现三类：

- **通道框架**：作为服务端接收客户端连接，管理连接与身份绑定，在通信工具与客户端之间转发消息和附件。
- **通道客户端**：作为客户端接入通道服务端，向调用方提供收消息、发消息、下载附件的回调接口；附带的命令行客户端用于手工联调。
- **Web 通道实现**：同时实现 Web 通信工具与通道适配层，提供管理员后台、普通用户接入、群组与用户管理、消息与附件的本地存储，并以独立的 Web 前端作为管理员界面。

通道实现可以只作为对接层接入已有通信工具，也可以像 Web 通道一样同时包含通信工具本身。详见 [kissbot-channel](components-design/kissbot-channel.md)、[kissbot-channel-client](components-design/kissbot-channel-client.md)、[kissbot-channel-web](components-design/kissbot-channel-web.md)。

### 3. 记忆系统（kissbot-memory-*）

所有 agent 共用同一套记忆系统。其设计基础是把全部原始记忆完整保存，并在其之上建立可替换、可重建的索引结构，以此在保证记忆完整性的同时降低记忆召回难度。

- **记忆基础库**：定义记忆文件系统的目录布局、记录类型与路径规则，并提供目录管理与索引查询能力。
- **记忆存储服务**：接收 agent 推送的通道记录并持久化，提供按时间与条数的查询能力，在有新数据时广播通知。
- **摘要记忆服务**：把原始记忆切分为 case（专案）并生成摘要，按新消息定位所属 case，为调用方提供摘要与原文片段。
- **自我认知服务**：管理 agent 的客观设定与角色设定，供 agent 构建系统提示词，并提供搜索与补全能力。

详见 [kissbot-memory](components-design/kissbot-memory.md)、[kissbot-memory-store](components-design/kissbot-memory-store.md)、[kissbot-memory-struct-summary](components-design/kissbot-memory-struct-summary.md)、[kissbot-memory-ego](components-design/kissbot-memory-ego.md)。

### 4. 管理界面（kissbot-agent-config、kissbot-memory-manage）

面向管理员的前端应用。智能体配置界面用于查看与修改 agent 的配置，记忆管理界面用于查看与维护记忆数据。二者当前只是可独立构建与启动的应用骨架，尚未接入后端服务。

### 5. 公共基础库（kissbot-api、kissbot-config、kissbot-security、kissbot-llm、kissbot-mcp）

被多个组件复用的基础能力：

- **API 定义库**：定义组件间通信的数据契约与统一响应格式。
- **公共配置库**：只读加载一份公共配置文件，供各组件按路径提取自己的配置段。
- **安全库**：提供 API key 认证的校验器、HTTP 中间件与 WebSocket 握手过滤。
- **LLM 基础库**：对接模型服务商（两种协议）、失败重试、模型列表查询，以及单个会话上下文的保存与版本管理。
- **MCP 基础库**：按 MCP 规范实现服务发现、工具列表、工具调用三项能力，并提供 kissbot 的工具分组与级联扩展。

## 二、组件间通信

| 发送方 | 接收方 | 通信内容 | 通信时机 |
|--------|--------|----------|----------|
| Agent（pipeline） | 通道服务端 | 绑定身份、心跳、下行消息、附件下载请求 | 启动装配后绑定输入身份；有回复时发送；需要附件时请求 |
| 通道服务端 | Agent（pipeline） | 上行消息、群组变更通知、用户移除通知、附件数据、心跳 | 外部消息到达时；群组或用户变化时；Agent 请求附件时 |
| Agent | LLM 服务商 | 模型调用请求、模型响应、模型列表查询 | agentic loop 的每一轮；校验模型时 |
| Agent | 记忆存储服务 | 推送通道记录；按最近条数与时间范围查询记忆 | 收到上行消息、发出下行回复时写入；上下文超长且选择记忆回溯时查询 |
| Agent | 摘要记忆服务 | case 定位、case 摘要、case 结尾原文查询 | 摘要记忆 pipeline 处理批次、重建 case 上下文时 |
| 记忆存储服务 | 摘要记忆服务 | 新通道记录通知（附记忆范围与通道身份） | 每批记录写入完成后 |
| Agent | 自我认知服务 | 读取 agent 元数据、个体识别、角色设定 | 建立会话并生成系统提示词时 |
| Agent（Station） | 子 Station | 工具列表、工具调用（MCP） | 查询工具时；执行子站工具时 |
| 其他 Station | Agent（Station） | MCP 服务发现、工具列表、工具调用 | 被上级 Station 查询或调用时 |
| 管理客户端（外部工具） | Agent | 管理 API：配置读写与运行期管理 | 管理员调用时（仓库内的两个管理界面尚未接入该接口） |
| Web 前端（管理员） | Web 通道 | 管理、发消息、附件上传下载、事件订阅 | 管理员操作时；页面保持事件订阅 |
| Web 通道 | Web 前端（管理员） | 实时推送消息与事件 | 消息落盘后；群组或用户变化时 |
| 普通用户或外部客户端 | Web 通道 / 通道服务端 | 通道客户端的绑定、收发消息、附件传输 | 客户端接入与收发消息时 |
| 记忆存储服务、摘要记忆服务 | 文件系统 | 共享读写记忆目录 | 持续 |

通信方式上，请求-响应使用 HTTP，实时消息与通知使用长连接，Web 前端的事件推送使用服务端推送，记忆的原始数据与索引数据通过共享文件系统交换。各方式的实现约定见 [communication](../spec/communication.md)。

## 三、关键设计

### 统一的公共消息格式

通道与记忆共用一套消息格式：文本消息直接携带文本；复合消息由多个内容项组成，可嵌套，一项消息可以同时包含文本、附件、思考与工具调用等内容；附件类内容只携带附件的标识与元信息，附件本体由通道实现保存与访问，记忆只保存记录本身。思考与工具调用、工具结果作为通道记录的组成部分写入，与回复文本一起构成一条记录，不单独成条。

### 记忆的存储与索引分层

原始记忆只做追加式保存，不做加工；索引结构（当前为摘要记忆）从原始记录中读取数据并构建自己的组织，原始记忆不受索引结构变化的影响。索引结构可以重建，重建只影响它自己的数据范围。新增记忆的登记与索引计算解耦：存储服务只广播「哪个记忆范围的哪个通道有新数据」，实际的归档与摘要计算推迟到显式入口（定位、手动触发、重建）时进行。

### 两种记忆组织模式

记忆按「agent + 角色」划分范围，并支持两种组织模式：

- **角色记忆**：一个 agent 角色对应一段连续记忆，跨事件累积。
- **事件记忆**：在角色之下按事件划分，一个事件一段记忆，彼此隔离。

两种模式共用同一套存储与索引机制，仅在记忆范围标识上不同。调用方以「角色 + 可选事件」表达记忆范围，文件与目录命名由记忆基础库统一构造。

### Agent 的 pipeline、输入身份与会话

Agent 启动时按配置装配若干条 pipeline，每条 pipeline 的身份为「agent + 角色」，并声明自己订阅的输入身份（通道、通道内的用户、群组）。一条上行消息按输入身份交给唯一一条 pipeline；同一输入身份只绑定一条 pipeline，先绑定者生效。pipeline 在运行期维护当前事件，切换事件不改变输入身份，也不重建 pipeline。会话上下文、记忆读写范围、当前事件都由 pipeline 持有；会话上下文的本地保存与版本管理由 LLM 基础库承担。

### Agent 的回复目标

回复目标由 pipeline 自己的回复通道配置决定，与消息从哪个通道到达无关；带记忆的 pipeline 未配置回复通道时只写入记忆、不发送回复，无记忆对话不发送回复。发送前校验目标身份仍被某条 pipeline 绑定，避免向已失效的通道发送。

### Agent 的双重自我认知

Agent 的自我认知分为客观设定与角色设定。客观设定描述 agent 自身（身份标识、描述、禁止事项、自主目标）以及它所认知的外部个体（名称、身份、关联的通道身份、个体间关系）；角色设定以角色为单位描述该角色的定位、禁止事项、自主目标，以及与其他角色的关系。Agent 在建立会话时读取这些信息并生成系统提示词。

### 工具分组与白名单

工具在注册时即带有所属分组；Station 及其子站提供的工具在对外查询时都携带分组。会话按分组白名单决定可用工具集合，白名单在 agent 侧按工具分组过滤，工具列表请求本身不做分组过滤，因此同一棵 Station 树可以被不同会话以不同范围使用。

### 组件形态与进程拓扑

Agent、记忆存储、摘要记忆、自我认知、Web 通道均为独立进程，各自监听自己的服务端点；通道框架、通道客户端、记忆基础库、LLM 基础库、MCP 基础库、API 定义库、公共配置库与安全库以程序库形式被其他组件引用。服务之间只通过 HTTP、长连接与共享文件系统交互，进程内部不共享运行态。对外暴露的服务通过代理层转换为 HTTPS 与 WSS，认证由安全库统一提供。
