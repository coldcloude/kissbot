# 系统设计文档

## 概述
本项目实现一个AI智能体及其记忆系统、消息系统等附属组件。

## 一、组件体系

### 1. Agent
智能体组件，由 Nexus（LLM 通信枢纽）和 Station（Tool 执行主机）两个内部模块组成，模块职责与内部结构详见 [system-design-agent](system-design-agent.md)。Agent 的 LLM 调用与会话上下文本体依赖 **LLM 基础库（kissbot-llm）**。

Agent 程序当前启动时同时装配 Nexus 与 Station（Station 单例 + station MCP 服务端，可被远程 station 作为 sub 调用）；同一系统内可运行多个 agent 实例，各实例可对接不同的 LLM 模型或服务于不同的场景。

Agent 除了根据外界信息给出回应外，还可以主动获取信息并据此行动。可以为 agent 设计自主行动的目标，agent 据此执行信息收集、信息反馈、自动工具调用等。

> 注：上下文超长时的记忆回溯由 Nexus 的消息发送器完成，不经由 station 执行；LLM 主动发起的记忆搜索工具（memory-struct）待实现组件落地后接入。

### 2. LLM 基础库（kissbot-llm）
把「与模型服务商通信」和「会话上下文管理」从 agent 中抽出的基础库，供需要 LLM 的模块复用（当前使用方为 Agent；摘要记忆、笔记工具等模块后续接入）。组件按调用方给出的 provider 配置完成模型调用（OpenAI 兼容 / Anthropic 两种协议、失败重试、模型列表查询），并按调用方给出的会话标识管理 LLM 上下文（内存消息 + 本地缓存 + 历史归档）。

组件不持有配置、不做配置落盘与继承链合成、不管会话集合，也不依赖 MCP 与任何业务身份概念；provider 实例复用（工厂去重）、provider 分派与有效配置解析由调用方的 provider 管理器完成（agent 中为 ProviderManager）。详见 [kissbot-llm 组件设计](components-design/kissbot-llm.md)。

### 3. 消息通道（Channel）
连接外部系统的桥梁。定义统一的 Messenger 接口（通讯应用接入标准，包含消息收发等功能），提供通道管理器作为核心协调层。具体的通讯应用接入由通道实现组件完成。

**通道实现组件**：实现 Messenger 接口，负责连接具体的外部系统（如 Web 页面、QQ 等），实现用户管理、群组管理、消息收发、附件管理等功能。通道实现可以是仅作为对接层接入现有消息工具（如 QQ 机器人），也可以是包含消息工具和对接层的完整实现（如 Web 前后端）。

### 4. 记忆系统
所有 nexus 共用同一套记忆系统，设计为在保存全部原始记忆数据的基础上，对接各种记忆提取、归纳、索引的结构，以便在保证记忆完整性的同时，降低记忆召回的难度。

**记忆基础组件**：定义记忆文件系统的目录结构，提供目录管理和索引查询框架。提供路径构造接口——推送方和查询方传入 `(agent-id, year, suffix)`，由本组件拼接完整路径。

**记忆存储组件**：收集 nexus 推送的全部原始消息（包括 channel 消息、思考内容、工具调用等类型）并持久化存储，提供记忆推送和查询 API。有新数据时通知各已连接的记忆结构组件。其中 channel 消息使用统一的公共消息格式。

**记忆结构框架**：定义记忆结构构建的标准接口。具体实现由独立的记忆结构实现组件完成。

**记忆结构实现组件**：读取记忆存储组件中的原始记忆记录，构建特定索引结构（如摘要索引、最近记忆索引等）。摘要记忆实现组件把记忆切分为 case（专案）、生成 case 摘要，并按新消息定位 case 提供上下文，详见 [kissbot-memory-struct-abstract](components-design/kissbot-memory-struct-abstract.md)；记忆搜索工具供 nexus 通过 tool call 调用（预留）。

### 5. 自我认知组件（Memory-Ego）
管理和获取 agent 的自我认知设定。提供 agent 元数据、个体识别信息、角色设定等数据的存储和查询能力。

### 6. API 定义
定义各组件间通信的标准数据结构和统一的响应格式，是组件间数据交换的契约层。内部模块与设计原则详见 [system-design-api](system-design-api.md)。

### 7. 安全组件
多种安全模块统一放在安全组件中，当前模块如下：
- **认证模块**：为所有模块提供统一的认证能力。
- **配置模块**：定义安全配置（通用 API 密钥、管理端 API 密钥），从公共配置中读取安全相关的配置项。

### 8. 公共配置组件
集中管理所有组件的配置信息。各组件从一份公共 JSON 配置文件中提取各自需要的部分。

**公共配置组件**：加载 JSON 配置文件（路径可由环境变量指定，未设置时使用默认路径），提供层级化的配置访问接口（按点号路径导航）。组件间通过点号路径解耦。

**网络地址配置**：定义各组件访问其他服务的 URL（memory-store、memory-ego 地址），统一从该配置中读取外部服务地址（详见 [system-design-api](system-design-api.md)）。

**安全配置**：所有 API key 统一归入 `security` 配置段，由 kissbot-security 提供统一访问接口。各组件通过安全配置模块获取认证所需的 key。

### 9. 管理界面
提供 Web 界面的管理工具集，包括：
- **智能体配置界面**：配置 nexus 使用的 LLM API、连接的 station、记忆模式，以及各类组件地址
- **记忆管理界面**：查看和管理记忆存储文件，配置记忆推送

## 二、组件间通信

### 通信总览

| 发送方 | 接收方 | 通信内容（方向） | 通信时机 |
|--------|--------|-------------------|----------|
| nexus | 消息通道 | 绑定请求（→）、下行消息/回复/思考（→）、附件下载请求（→）、心跳（↔） | nexus 启动时绑定；有消息回复时；需要附件时 |
| 消息通道 | nexus | 上行消息/用户消息（→）、群组变化通知（→）、附件数据（→）、心跳（↔） | 外部消息到达时；群组变化时；nexus 请求附件时 |
| nexus | station | tool call 请求（→）、tool result 响应（←） | agentic loop 内需要时 |
| station | 子 station | MCP 请求-响应：工具列表查询、工具调用（↔） | 级联查询工具与远程工具调用时 |
| nexus | 模型提供方 API（经 kissbot-llm） | 模型调用请求（→）、模型响应（←） | agentic loop 每轮；/model 校验模型列表时 |
| nexus | memory-store | 推送记忆记录（→） | 每条消息产生时（含收发的通道消息） |
| nexus | memory-struct-* | case 定位请求（→）、上下文（←）；记忆查询请求（→）、查询结果（←） | 预留：新消息定位与 LLM 记忆搜索工具均未接入（实现模块为 kissbot-memory-struct-abstract） |
| nexus | memory-ego | 读取自我认知设定（→）、返回设定（←） | 新建会话设置系统提示词时；/agent、/role 校验时 |
| memory-store | memory-struct-* | 新数据通知（→） | 新数据到达时 |
| memory-store / memory-struct-* | 文件系统 | 共享读写记忆文件（↔） | 持续 |
| 通道前端（浏览器） | 通道后端 | 消息收发、群组管理、附件操作（↔） | 用户操作时 |
| 通道后端 | 通道前端（浏览器） | 实时推送新消息（→） | 持续 |
| 智能体配置界面 | nexus | 读取/更新配置（↔） | 用户操作时 |
| 智能体配置界面 | station | 读取/更新配置（↔） | 用户操作时 |
| 记忆管理界面 | memory-store | 查看管理记忆（↔） | 用户操作时 |
| 记忆管理界面 | memory-struct-* | 查看管理（↔） | 用户操作时 |
| 记忆管理界面 | memory-ego | 查看管理（↔） | 用户操作时 |

## 三、关键设计

### 统一的公共消息格式
channel 和 memory 使用统一的公共消息格式。msg_type 为 text 时 content 为实际文本；multi 时 content 为 JSON 列表，每个元素包含 msg_type 和 content 两个字段；其他类型 content 为全局唯一 key——channel 通过 key 关联附件，memory 按 key 存储二进制内容。

### 记忆组织模式
suffix 由调用方按记忆模式拼接，本组件不做解析。支持两种记忆组织模式：
- 角色记忆：suffix 为角色标识，按角色组织所有历史记录
- 事件记忆：suffix 为角色标识加事件标识，按事件隔离上下文

### 摘要记忆的 case 组织
摘要记忆实现组件以 (agent, 角色) 为作用域把记忆组织成一棵 case（专案）树，每个 case 自包含原文副本与摘要，父 case 摘要覆盖其子 case。作用域分两级：**角色**（`AgentRole { agent_id, role }`，不含 event）决定 case 树——同一角色的角色模式与事件模式**共用一棵树**（同一句柄、同一目录）；外部传入的 `role` 是 **role-event 记忆后缀**，决定输入与状态（原始记录读取、水位、当前 case 指针、模型会话都按后缀区分）：无 `-` 为角色模式，含 `-` 为事件模式（按第一个 `-` 拆分，前半为角色名、后半为事件标识；角色名不允许含 `-`，事件标识可以含 `-`）。角色模式的记录经模型按 case 分组并多层归并，新 case 名为 `role-{模型给出的名称}`（名称只含英文字母、数字与 `-`，重名时追加 `-2`、`-3`…）；事件模式的整个后缀固定归入 `event-{事件标识}` 顶层叶子 case，不参与角色模式的判定，两种模式互不并入。记忆变更通知只登记「哪个记忆后缀哪个通道有新数据」，归档只在定位与手动触发（或重建）时进行（各通道单独成批），case 树/摘要/原文查询只读。新消息到达时先与该消息所在通道的当前 case 比对，未命中再自顶层逐层下探定位（当层候选只有角色 case），需要新建时立即建出 case 并同一次拿到名称与摘要（只有消息的组也建，记忆条数为 0，但名称与摘要当场就有）；定位会把新消息与该通道的待归档记录去重后合并成一批一起分析，同一条消息只分析一次，消息自身不落盘。重建只清空本次记忆后缀所属模式的那部分子树与该后缀的指针/水位。case 之间的关联关系以及关联 case 摘要纳入上下文为预留。

### nexus 与记忆系统的交互
nexus 与记忆系统的交互区分两种模式：
  - agentic loop 外：直接调用 API 读取自我认知设定、推送记忆到存储组件、上下文超长时从存储组件回溯打包
  - agentic loop 内：预留——由 LLM 通过记忆搜索 tool 从记忆结构组件查询记忆（不记入记忆）

### 会话与绑定
一个 nexus 可同时管理多个会话。nexus 按每个绑定 channel 的 agent_id（空/缺省 = 保留 agent "0"）、role_name、mode 将所有绑定项的信息去重，每个 agent_id+role_name+mode 组合为一个会话；各会话拥有独立的 LLM 上下文、记忆读写范围、pipeline 配置与模式状态，消息按来源 channel 对应的绑定配置路由到对应会话；记忆读写直接用 agent_id 定位（配置即 agent_id）。会话的回复目标由 (agent, role) 级回复通道配置（/bind-outgoing、/unbind-outgoing）决定，未配置则只存不回复。

### Agent 的自我认知机制
每个 agent 具有双重自我认知设定：
- **客观设定**：每个 agent 一份，包括身份标识（个体名称、描述）、个体识别信息（个体名称、和agent的关系、和其他个体的关系、关联的消息通道身份）、禁止事项和自主运行目标
- **角色设定**：每个 agent 可有多份，以角色名称为标识，包括角色描述、禁止事项、自主运行目标、和其他角色的关系、其他角色关联的个体信息

nexus 在新建会话时读取自我认知信息，构建到系统消息中（保留 agent、读取失败或未配置时回退默认提示词），使 agent 知道自己是谁、面对什么个体、扮演什么角色。

### 通道实现组件的消息存储
- 当通道实现仅作为对接层时，不存储历史消息，所有历史消息由记忆存储组件保存
- 当通道实现为包含消息工具的完整实现时，应有消息和附件存储等功能
