# 附件传输机制

> 说明通道框架的附件两阶段表示与分块传输，以及各通道实现的职责边界。

## 一、两阶段表示

1. **发送阶段**：消息内容里只有附件元信息（文件名、MIME、字节数），不含任何存储标识。
2. **注册阶段**：通道实现把元信息注册为「存储标识 + 传输标识」，并用附件响应形态替换原内容；替换会递归处理复合内容里的嵌套附件。
3. **传输阶段**：发送方按传输标识分块上传数据；接收方按存储标识请求下载。

存储标识是附件的永久标识，由通道实现决定编码方式；传输标识是本次传输的路由标识，由框架在注册或下载请求时分配。两者分离使同一附件可以被多次独立传输。

## 二、上传

- 客户端按传输标识连续发送二进制分块；每块携带传输标识、本块大小、块偏移与数据。
- 服务端解析帧头，按传输标识找到通道实现与该次传输声明的总大小，交给通道实现写入。
- 通道实现返回写入结果（当前进度、错误码、错误信息），框架把该结果作为该帧序号对应的响应返回。
- 框架只按「已写入大小达到声明总大小」或写入失败判断结束并删除传输项；它不纠正乱序。声明的总大小是唯一完成判据：声明错误会导致上传永远不完成。
- 顺序与幂等语义由通道实现负责：常见的做法是「偏移落后于当前进度视为重复块并返回成功，偏移超前视为乱序并返回错误与当前进度，由发送方纠正」。

## 三、下载

1. 客户端携带存储标识请求下载头；框架校验该用户绑定在本连接。
2. 通道实现返回附件信息与为本次下载新分配的传输标识，框架登记下载项。
3. 框架先返回下载头响应，再调用通道实现启动推送。
4. 通道实现逐块向框架申请预组帧：框架按传输标识找到对端连接、取新序号、预写帧头并返回可追加缓冲；通道实现读入数据后由框架发送，并等待该序号的确认。
5. 确认错误或传输失败即停止；最后一块发送完成或出错后删除下载项。

推送是停止等待式的：发一块、等一块确认，因此不会在客户端未跟上时持续灌数据。

## 四、能力边界

- 没有校验和、没有重传、没有断点续传；中断后只能重新发起传输（下载会得到新的传输标识，上传需要重新注册附件）。
- 没有并发块传输，同一附件的数据按序处理。
- 传输标识在框架侧是进程内全局自增的，不按 messenger 分组。

## 五、通道实现的职责

各通道实现需要提供：

- 上传分块的写入与进度反馈（含顺序、幂等与乱序错误码）。
- 下载请求的解析：把存储标识解析为附件信息与数据源，并分配传输标识。
- 下载推送的驱动：按块读取并交给框架发送，处理确认结果。
